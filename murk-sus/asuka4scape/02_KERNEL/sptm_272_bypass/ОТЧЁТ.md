## 1. Что такое SPTM в этой сборке

SPTM (Secure Page Table Monitor, EL2) — владелец трансляций. Ядро (EL1) не правит
page tables само, а просит SPTM через dispatch-таблицы. Для GPU (`/arm-io/sgx`,
AGX) SPTM держит отдельный UAT: `gpu-region` — регион, в котором лежит **TTBAT**
(таблица баз трансляций контекстов GMMU).

Инициализация: `FUN_0xfffffff0270afb68` («UAT Global»).

```
/arm-io/sgx:
  agx-address-space-mgmt-mode      -> instance[0x10]
  gpu-region-base                  -> instance[0x68]   <-- TTBAT paddr
  gpu-region-size                  -> instance[0x70]   (в страницах, /0x4000)
  gfx-shared-region-base/size      -> instance[0x128]/[0x130]
  gfx-shared-l2-region-base/size   -> instance[0x118]/[0x120]  (строго 1 страница)
  gfx-handoff-base/size            -> instance[0x138]/[0x140]
  uat-enforce-gpu-carveout         -> instance[0x1b0] (по умолчанию 1)
  uat-vaddr-size                   -> instance[0x1b1]
  uat-segment-limit                -> instance[0x1c0] (по умолчанию 0x40)
  uat-mapping-limit                -> instance[0x1c8] (по умолчанию 0x100)
```

`gpu-region-base` пишется в `instance+0x68` дважды (в двух ветках режима
address-space-mgmt-mode), размер — в `+0x70` как `size >> 14`.

## 2. UAT MAP_BEGIN — точное поведение

`FUN_0xfffffff0270adf30` (dispatch entry, вызывается из таблицы `0x2701c148` и
`FUN_0x270ae700`). На каждую страницу диапазона:

```
paddr = seg_base + cur*0x4000            // далее маска 0xfffffffff000
pte   = walk(ttbr, va, 3, &out)          // FUN_0x270ad14c
type  = fte_type(dispatch, ...)          // &DAT_0x27019e80[...]
perm  = 1 или 2 (по типу)
if (paddr == instance[0x68] && type in {2,3,5,6,7,9,10}) -> panic
if (paddr != instance[0x68]) FUN_0x270e1168(paddr, perm)
pte = paddr | flags | type | ...
```

Ключевые адреса:

| Адрес | Роль |
|---|---|
| `0xfffffff0270adf30` | UAT MAP_BEGIN |
| `0xfffffff0270ae194` | вызов проверки прав |
| `0xfffffff0270e1168` | проверка FTE/прав для paddr |
| `0xfffffff0270e1570` | фиксация (commit) прав FTE |
| `0xfffffff0270abc74` | release/invalidate контекста + проверка TTBAT-записей |
| `0xfffffff0270921b8` | `uat_instance` |
| `instance+0x68` | `gpu-region-base` (TTBAT paddr) |
| `0x27092228` / `0x27092230` | битовая карта допустимых типов и max permissions по dispatch id |
| `0x270914f0` | FTE-таблица (16 B на страницу) |
| `0x2701f000` | таблица имён violation-кодов |

Проверка `FUN_0xfffffff0270e1168`:

1. FTE по paddr: `0x270914f0 + ((paddr - 0x70921c8)>>14)*0x10`, иначе `FUN_0x270df750`.
2. `type = FTE[+2]`; `allowed = (&0x27092228)[type*0x90] >> (dispatch_id-1)`: тип
   должен быть разрешён текущему IOMMU.
3. `maxperm = (&0x27092230)[type*0x90]`; `maxperm < perm` → violation.
4. для типа 6 — проверка IO range restriction;
5. `FUN_0xfffffff0270e1570` — финальное применение.

`FUN_0xfffffff0270abc74` при release контекста проверяет, что обе половины записи
TTBAT (`{paddr, flags}`) имеют бит valid; иначе panic
`Valid context ID but the TTBAT already contains invalid entries`. Это
бухгалтерия SPTM по записям TTBAT, а не проверка содержимого PTE.

Новые в 27.2 имена нарушений (таблица `0x2701f000`, слоты `+0x118`, `+0x158`):

```
VIOLATION_UAT_ILLEGAL_TTBAT_MAPPING   (строка 0x2700513f)
VIOLATION_UAT_ILLEGAL_TTBAT_LOCK      (строка 0x27005256)
```

То есть класс атаки «подменить TTBAT и увести GMMU на свои page tables» в 27.2
известен и обложен проверками; при этом точечный скип для `paddr == gpu-region-base`
в MAP_BEGIN **остался**.

## 3. Почему скип вообще опасен

Если добиться вызова MAP_BEGIN с `paddr = gpu-region-base` и leaf-типом, SPTM:

- не проверяет FTE-права для этой страницы (`FUN_0x270e1168` пропущен);
- пишет PTE на TTBAT-страницу в выбранный UAT с запрошенными правами.

Дальше устройство, которому принадлежит этот UAT (GPU), получает RW-доступ к
странице TTBAT. Запись в TTBAT = выбор собственных page tables для контекста
GMMU. Дальше GMMU ходит по нашим таблицам, и GPU DMA читает/пишет произвольную
физическую память — вне контроля SPTM над CPU-трансляциями. Это и есть «снять
контроль»: ядро и SPTM больше не единственные владельцы физической памяти.

Цепочка в терминах примитивов:

```
userland
  -> [1] kernel/IOGPU путь, дающий paddr = gpu-region-base в UAT MAP_BEGIN
  -> [2] PTE на TTBAT-страницу с RW в UAT, который использует GPU
  -> [3] перезапись записи TTBAT: свой контекст -> своя таблица
  -> [4] GPU DMA по нашим PTE: произвольный phys R/W
  -> [5] kernel R/W, патчи, unsigned code
```

[1] — единственное недостающее звено. Всё остальное обеспечено самим SPTM.

## 4. Чего не хватает и почему это не «ещё чуть-чуть»

В присланном `.rep` — ядро 27.0.0/T8122, а не 24B115/T8110 (см. §0). Даже если
бы там был нужный билд, звено [1] — это поиск kernel-бага с контролем paddr, а не
чтение одной функции:

- `paddr` в UAT-запрос приходит из pmap/IOGPU, а не из userland;
- тривиальные источники (IOSurface, compressed planes, AVE/ANE) в 27.2 закрыты
  (отчёты 27.2-ФИНАЛ, KASLR/CoreTrust);
- без kernel R/W звено [1] достигается только багом в драйвере GPU/IOMMU.

Поэтому честный статус на этот заход: SPTM-примитив зафиксирован, полный байпас
не собран. Файл статуса: `STATUS_НЕ_РАБОТАЕТ.md`.

# Дополнение (2026-11-02, второй заход): проверка PA-контроля через IOSurface

## A. Что проверялось

Гипотеза: свойство `IOSurfaceAddress` у пользовательской поверхности даёт
произвольный физический адрес (PA control) и через UAT MAP_BEGIN с
`paddr == gpu-region-base` снимает контроль SPTM.

## B. Что найдено в 24B115 (kernelcache.release.iphone14b)

1. `IOSurfaceRootUserClient::externalMethod` — `0x9c3ee10`, таблицы
   `0x8068b90` (обычные клиенты) и `0x80694f0` (clients с
   `com.apple.private.gpu-restricted` / `com.apple.developer.gpu-restricted`).
   Селектор 0 (create surface) — `0x9c3888c`, одинаков в обеих таблицах.
2. Селектор 0 десериализует `structureInput` (`OSUnserialize`, `0x9c49764`),
   достаёт словарь свойств и вызывает `0x9c3ab8c` → `0x9c33c34` →
   `IOSurface::initWithProperties` `0x9c1a914`.
3. `initWithProperties` читает ключ `IOSurfaceAddress` (`0x789b134`,
   код `0x9c1dfc4`) и кладёт u64 в `surface+0x150` (`0x9c1e03c`).
   Единственный фильтр рядом — флаг `surface+0x308` (compressed surface):
   `IOSurface: Cannot use kIOSurfaceClientAddress with compressed iosurfaces.`
4. Из `surface+0x150` считаются `+0x158/+0x160/+0x168` (aligned addr/len/offset)
   в `0x9c1ad80..0x9c1adb8`.
5. Физическая ветка дескриптора — `0x9c1ea68`: `ldp x0,x1,[surf+0x158]`,
   `ldr x16,[surf+0x170]`; если `x16 == 0` → `task = NULL` →
   `IOMemoryDescriptor::withAddressRange(..., 0x20 /*physical64*/)`.
6. `surface+0x170` пишется в `0x9c1aa70..0x9c1aa84` из аргумента `x2`
   функции `initWithProperties`.
7. Цепочка аргументов от пользовательского клиента:
   `create 0x9c3ab8c` передаёт в `0x9c33c34`: `x1 = [client+0xf8]`
   (PAC-указатель на **owningTask**, записан в `0x9c3a324..0x9c3a334`),
   `0x9c33c34` передаёт его в `initWithProperties` как `x2` →
   `surface+0x170 = task != 0`.

## C. Вывод

Для поверхности, созданной через `IOSurfaceRootUserClient`, `surface+0x170`
всегда ненулевой (owningTask), поэтому `IOSurfaceAddress` трактуется как
**virtual64-адрес задачи**, а не как физический. Физическая ветка
(`task == NULL`) остаётся только у kernel-клиентов, которые фабрикуются
внутри kext'ов и наружу не отдаются.

Это совпадает с выводом `~/work/physaddr/REPORT.md` по `AppleM2ScalerCSCDriver`:
все user-reachable `withAddressRange` идут с `task != 0` (virtual64).

**Гипотеза «IOSurfaceAddress = PA control из песочницы» закрыта кодом.**

## D. Что осталось из непроверенного

- `IOSurface` `0x9c1ebf8`: путь физического дескриптора существует, но
  достижим только при `+0x170 == 0` (kernel client).
- IOGPU/AGX UAT: кто и с какими правами маппит `gpu-region-base`
  (`instance[0x68]`) в UAT пользовательского клиента — не найдено.
- Единственный не закрытый статикой класс — гонки VM/SPTM вокруг
  page-table страниц (SAPT), см. `VIOLATION_UAT_SAPT_*`; требуется
  динамика на устройстве.

# Дополнение 2: AGX и TTBAT (24B115)

## Что найдено

В `com.apple.AGXG14P` (VA 0xfffffff007112f20, код 0xfffffff008165300+):

| Строка | VA | Использование |
|---|---|---|
| `gptbat-ready` | `0xfffffff0071228fd` | `0x81ff1b4` |
| `ttbat-phys-addr-base` | `0xfffffff0071228e8` | `0x81ff224` |
| `AGXSecureMonitor` | `0xfffffff00711f1af` | `0x81db410` |

Функция `0x81ff0d0` (инициализация secure GART/монитора):

```
0x81ff1a8..1c0: getProperty("gptbat-ready")        -> x21
0x81ff21c..230: getProperty("ttbat-phys-addr-base") -> x?
0x81ff240:      поиск объекта по глобальному ключу
0x81ff29c..2c4: создание/выделение буфера:
                 gptbat-ready==0 -> factory(type=3, size=1<<page_shift)
                 иначе           -> factory(addr=0, size, dir=3)
0x81ff2d0..:    prepare/map, получение kernel VA, зануление страниц
```

Обе ветки — kernel-инициализация AGX. `ttbat-phys-addr-base` берётся из
device tree сервиса (`/arm-io/sgx`), не из userland. Это ровно тот
легитимный путь, ради которого в SPTM MAP_BEGIN оставлен скип проверки
для `paddr == instance[0x68]`.

## Следствие

Точечный скип SPTM не является «дырой по умолчанию»: он обслуживает
инициализацию secure GART, где адрес TTBAT — фиксированное свойство
платформы. Чтобы им воспользоваться, нужно подменить либо
`ttbat-phys-addr-base` (device tree, до запуска XNU), либо paddr в
UAT-запросе (kernel-примитив), либо заставить GPU записать в уже
замапленный TTBAT (firmware-путь AGXSecureMonitor / hibernation).

Первые два закрыты статикой (DT неизменяем из XNU после SPTM init;
user→paddr закрыт). Третий — единственный живой класс; он требует
динамики на устройстве и упирается в firmware AGX, а не в SPTM.

## Дополнение 5.1: селекторы 9/11 (any structIn)

`9` = `0x9c38b2c` (требует `structIn >= 0xd`), `11` = `0x9c38e54`.
Оба берут `structureInput` (ptr,len), первые 4 байта — surface id, затем
`OSUnserialize(ptr+0xc, len-0xc, 0)` и применяют результат:

```
sel9 : 0x9c3c3b8(client, buf, len, out)
         id = *(u32*)buf
         dict = OSUnserialize(buf+0xc, len-0xc, 0)
         obj = dict[key_806c9f0]
         apply -> 0x9c28220(surface, obj, len?, out)
                  -> 0x9c49ae4(obj) -> 0x9c255c8(surface, dict, x2, x3)
```

Длины: `end = buf + (u32)len`, разбор `[buf+0xc, end)` — без выхода за буфер,
`len` приходит из `IOExternalMethodArguments` и проверен диспетчером IOKit
(размер реального structIn). Классического переполнения длины нет; вся
семантика уходит в `OSUnserialize` и `0x9c255c8` (applier словаря).

Остальные any-size: 10 (`0x9c38c44`), 26 (`0x9c39448`), 46 (`0x9c39a78`),
47/48 (`0x9c39bdc`/`0x9c39cf4`), 50 (`0x9c39eb8`), 54 (`0x9c39f5c`).

# Стена (по состоянию на 2026-11-02)

Полный SPTM-байпас из sandbox-приложения на 24B115 сейчас недостижим.
Это не «не нашли», это закрытые двери, каждая проверена на устройстве или по коду:

1. **GPU/TTBAT** — `AGXAcceleratorG14P` client type 1 создаётся, но
   `getTargetAndMethodForIndex` не отдаёт ни одного метода: все селекторы
   0x00..0x37 → `0xe00002c2`. Приватный AGX-энтайтлмент обязателен.
   Без него firmware-путь к TTBAT (единственный, где SPTM-скип
   `paddr == uat_instance[0x68]` применим) недоступен.
2. **PA-контроль** — `IOSurfaceAddress` = virtual64 (подтверждено на устройстве),
   физическая ветка `IOMemoryDescriptor` при `task == NULL` только у kernel-клиентов.
3. **DART** — `0xe00002c2` на всех типах.
4. **Device tree** — `/arm-io/sgx` свойства не отдаются песочнице.
5. **IOSurfaceRoot** — 60 селекторов сняты; 9/11 = OSUnserialize с проверенной
   длиной, 27/28 = фиксированные смещения по маске; 34-40 (SharedEvent) — без UAF.
6. **Scaler** — 12 селекторов, все `withAddressRange` идут с owningTask
   (virtual64), физическая ветка только у kernel-клиентов.

Следствия:

- «Снять контроль SPTM» без kernel-примитива нельзя: SPTM валиден по построению,
  а единственный скип требует paddr, который userland не контролирует.
- Реальные пути остаются два: приватный AGX-энтайтлмент (тогда открывается
  firmware/TTBAT) или новый kernel-bug (тогда примитив, затем MAP_BEGIN).

Всё, что можно было доказать статикой и тремя рантайм-прогонами, доказано и
лежит в этом отчёте с адресами.

# Дополнение 6: Metal-соединение и регионы (рантайм, 24B115)
