# Три «лишних» блока 27.2 RC: IOMMU read-refcount проверяется в retype, hib и IUO — boot-time policy, не runtime-поверхность

**Кратко:** Разобрал, что дают три блока, которых нет в публичном диффе 27.2b3. (1) IOMMU read-refcount — это FTE-бухгалтерия: хелперы 0x270dd4e8 / 0x270dd558 и валидатор retype 0x270dd658; в валидаторе тип FTE индексирует таблицу 0x27092200 (stride 0x90), проверяется байт +1 == 3 и счётчик +0xc, а диагностические ветки (0x270dd7a8 / 0x270dd854 / 0x270dd894) теперь печатают «fte(%p), new_type(%s), page_flags(%u), read_refcnt(%d) iommu_read_refcnt(%u)», плюс отдельная проверка «iommu_read_refcnt (0x%hhx) > read_refcnt(0x%x) for FTE %p». То есть инвариант усилен: раздельный счётчик IOMMU-чтений не может превысить общий read-refcount, и это проверяется на переходе типа (retype), а не только при маппинге. (2) Hibernation-блок (VIOLATION_NVME_ILLEGAL_HIBERNATION_QUEUE_LATCH, enforce_no_hib_latch, /chosen/manifest-properties, лимит handoffPageCount) живёт в hibernate_restore.c и вызывается на boot/restore (xref 0x270bc720, 0x270bcb9c, 0x270e9350) — SPTM читает devtree и паникует при расхождении, из XNU после старта это не достижимо. (3) IUO-блок (sptm_is_iuou_or_iuos_device, sptm_allow_vm_isa_internal_guests, internal-use-only-unit) — тоже boot-policy: 0x270b2f80..0x270b30d8 парсит /chosen/manifest-properties и свойство internal-use-only-unit (0x270b300c), а строки-имена используются как аргументы паники (0x270b4214/0x270b4220). Вывод: runtime-поверхность SPTM в 27.2 RC относительно b3 не расширилась; всё новое — либо boot-time проверки, либо ужесточение инварианта refcount. Практический след: максимум, что может дать retype-путь — панику (DoS), не примитив.

## Target
SPTM 27.2 RC, build **24B115**, iPhone14,7 / T8110, `SPTM-820.40.24`.
Артефакт: `02_KERNEL/sptm/27.2/sptm.macho` (1 212 448 B); дифф-база — `02_KERNEL/sptm/27.0.1/sptm_27.0.1_t8110.macho`.

## Component
Новые (относительно 27.0.1 и публичного b3-набора) участки SPTM:
FTE lifecycle / retype, hibernation restore, boot-policy (IUO, DART clock).

## Primitive
Не примитив — классификация дельты: какие из новых блоков достижимы в runtime, а какие нет.

## Evidence

### 1. IOMMU read-refcount — это FTE-бухгалтерия, проверяется в retype
Границы функций (__TEXT_EXEC, VA `0xfffffff027098000`+):
```
0xfffffff0270dd4e8  bti c; and w8,w2,#0xff; cmp #4; strb w2,[x0,#4]   ; мелкий setter
0xfffffff0270dd558  ... ldrb w9,[x0,#2]                              ; тип FTE
                         add x8, x9, x9<<3 ; таблица 0x27092200 + type*0x90
                         ldrb w8,[x8,#1]; cmp #3; ldr w8,[x0,#0xc]   ; счётчик +0xc
0xfffffff0270dd658  ...                                              ; валидатор перехода типа
```
Внутри валидатора три диагностические ветки с новой строкой
`"%s(%s:%d) - fte(%p), new_type(%s), page_flags(%u), read_refcnt(%d) iommu_read_refcnt(%u)"`
(строка VA `0x270135f0`, xref'ы `0x270dd7a8`, `0x270dd854`, `0x270dd894`), а также отдельная
проверка `"%s: %s: iommu_read_refcnt (0x%hhx) > read_refcnt(0x%x) for FTE %p"`
(VA `0x2701359f`, ссылка идёт через таблицу сообщений, прямого adrp+add нет).

Смысл: у FTE теперь два счётчика чтения — общий `read_refcnt` и отдельный `iommu_read_refcnt`
(чтения со стороны IOMMU/GPU). Инвариант «iommu_read_refcnt ≤ read_refcnt» проверяется на
переходе типа (retype), а не только на map/unmap. Это ужесточение, а не новая дыра.

### 2. Hibernation-блок — boot/restore-time
```
VIOLATION_NVME_ILLEGAL_HIBERNATION_QUEUE_LATCH   (VA 0x27008a41, xref нет — через таблицу violation)
enforce_no_hib_latch                             (VA 0x2700931a) -> xref 0x270bc720, 0x270bcb9c
/chosen/manifest-properties                      (VA 0x2700700d) -> xref 0x270b3048
hib_header_copy->handoffPageCount < HIB_HANDOFF_PAGECOUNT_LIMIT (VA 0x270165dc) -> xref 0x270e9350
```
Код лежит в `hibernate_restore.c` (путь в строке), т.е. исполняется при восстановлении из
гибернации, до/вне нормальной работы XNU. SPTM читает devtree/chosen и паникует при
несоответствии; источник данных — загрузчик, не userland.

### 3. IUO / DART clock — boot-policy
```
0xfffffff0270b2f80 .. 0x270b30d8: разбор /chosen/manifest-properties;
    чтение свойства "internal-use-only-unit" (0x270b300c -> строка 0x27006fda);
    ветки паники 0x270b4214 / 0x270b4220 подставляют имена
    "sptm_allow_vm_isa_internal_guests" (0x27006fb8) и "sptm_is_iuou_or_iuos_device" (0x27006ff1)
    в формат сообщения — это диагностика, а не отдельные проверки в рантайме.
0xfffffff0270c78bc / 0x270c78e0: "sptm_t8110dart_skip_disable_clock_protection_write"
```
Всё это — инициализация и boot-политика (внутренние юниты Apple, clock protection у DART),
на розничном устройстве ветки IUO не включаются.

## Reproduction
1. Взять `sptm/27.2/sptm.macho`, `__TEXT_EXEC` fo `0x94000`, VA `0x27098000`.
2. Дизасм 0x270dd4e8 / 0x270dd558 / 0x270dd658; строки — в `__TEXT` (`__cstring`, VA `0x27004000`+).
3. Xref'ы — adrp+add сканер; таблица violation — `0x2701f000` (по прежнему отчёту).
4. Hib/IUO — дизасм 0x270b2f80 и 0x270bc6xx.

## Reliability
Статический разбор двух сборок (27.0.1 и 27.2 RC), адреса перепроверены xref'ами.
Функциональные имена — по строкам и форме кода (SPTM stripped), поэтому «retype» — вывод по
`new_type` в сообщении и по индексации таблицы типов, а не по символу.

## Impact
- Runtime-поверхность SPTM в 27.2 RC **не расширилась**: новых пользовательски достижимых
  веток нет; добавлены boot-time паники и ужесточение инварианта refcount.
- Значит публичная карта b3 + наши три блока не дают новой точки входа. Максимум от
  retype-пути — паника при рассогласовании счётчиков (DoS), а не примитив.
- Экономия времени: не искать «новые дыры 27.2 RC» в hib/IUO — это не тот слой.

## Next step
1. Если возвращаться к SPTM — только через paddr-контроль в UAT MAP_BEGIN (отчёт id 10),
   т.е. искать kernel/IOGPU-примитив, а не новые проверки в SPTM.
2. Проверить, кто в XNU вызывает retype для GPU-кадров (pmap/IOGPU), и может ли ошибка
   в порядке inc/dec довести до новой паники — это диагностический тест устройства.
3. Держать в уме: hib-путь может быть интересен при атаке на загрузчик (не из песочницы).

## Confidence
high — по адресам и форме кода (hib/IUO — boot-time, refcount — валидатор retype).
medium — точная семантика нового счётчика (какие именно операции его инкрементируют).
Опровергнет: находка user→kernel пути, вызывающего retype/hib-код после старта,
