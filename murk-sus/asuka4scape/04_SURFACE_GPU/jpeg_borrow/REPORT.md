# JPEG borrow: потребители `session+0x4c8`

Kernelcache 27.2 / 24B115 (SDK 24B112). Для `__TEXT_EXEC`: `foff = va - 0xfffffff007004000`.
Kext: `com.apple.driver.AppleJPEGDriver` 8.1.7, load `0xfffffff007519490`,
`__TEXT_EXEC` = `0xfffffff008c7b8a0` (foff `0x1c778a0`, size `0x2e008`).
Все адреса ниже — VA 27.2, если не сказано иное.

## Итог

Ветка «borrow» реальна и достижима, но **рабочим UAF в этой сборке не становится**.

- Указатель `in+0x84` пишется в `session+0x4c8` только в двух местах и только при
  `inputSize <= 0xf7f/0xc03` **и** `[in+0x30] == 0`.
- Потребителей ровно два: инициализатор/вайп сессии и copy-to-e8, причём второй
  вызывается из callback'а, который исполняется **синхронно внутри того же
  `startDecoder`**, до возврата в external method.
- Сессия (`kalloc_type` desc `0xfffffff007e2c498`) создаётся в начале
  `startDecoder`, используется gate-call'ом и уничтожается в конце той же
  функции. Наружу `x21` не сохраняется ни в клиент, ни в очередь, ни в глобал
  (единственная запись — self-pointer `session+0x80`).
- Пока external method не вернулся, `structureInput` (он же `args+0x30`, он же
  `x19`) жив. Все чтения `+0x4c8` укладываются в это окно.

Латентность остаётся только на будущее: кэш сессии между вызовами, async
`runAction` или повторный init живой сессии после borrow превратят это в UAF.
Ни одного из трёх условий в 27.0/27.2 нет.

## Где пишется

### startDecoderExt — `0xfffffff008c86024`

| шаг | адрес | что |
|---|---|---|
| размер входа | `0x8c86174` | `ldr w25,[x19,#0x7c]` (поле `newHeaderSize`) |
| проверка 1 | `0x8c8619c` | `cmp w25,#0x1000; b.ls` — иначе reject |
| проверка 2 | `0x8c8620c..0x8c8622c` | `%12 == 0` (mul `0xaaaaaaab`, `ror #2`), иначе reject |
| проверка 3 | `0x8c86258..0x8c86260` | `lsr x1,x25,#2; cmp w25,#0xf7f; b.ls 0x8c86310` |
| флаг | `0x8c860fc` | `ldr x8,[x19,#0x30]` (output-структура) |
| borrow | `0x8c86310` | `add x23,x19,#0x84` |
| guard | `0x8c86314` | `cbz x8,0x8c8634c` — borrow только при `[in+0x30]==0` |
| запись | `0x8c8634c` | `str x23,[x21,#0x4c8]` |
| count | `0x8c86350/54` | `mov w8,#0x3df; str x8,[x21,#0x4d0]` |

Если `[in+0x30] != 0`, вместо borrow идёт `vec_reserve(session+0x4d8)` +
`memcpy(size&0xffc)` из `in+0x84` (`0x8c8631c..0x8c86344`) — тоже внутри вызова.

### startDecoder2024 — `0xfffffff008c87038`

| шаг | адрес | что |
|---|---|---|
| размер | `0x8c87174` | `ldr w26,[x19,#0x7c]` |
| проверка 3 | `0x8c8726c..0x8c87274` | `lsr x1,x26,#2; cmp w26,#0xc03; b.ls 0x8c87324` |
| borrow | `0x8c87324` | `add x23,x19,#0x84` |
| guard | `0x8c87328` | `cbz x8,0x8c87368` |
| запись | `0x8c87368` | `str x23,[x21,#0x4c8]` |
| count | `0x8c8736c/70` | `mov w8,#0x300; str x8,[x21,#0x4d0]` |

`x21` = сессия, `x19` = inputJPEGStruct (`x1` функции). Обе функции получают
`x1 = [args+0x30]` из диспетчерских обёрток: `0x8c8fb84`, `0x8c8fbb8`,
`0x8c8fde0`, `0x8c8fe08` (`ldr x1,[x2,#0x30]`), `x2` = `[args+0x58]`
(outputJPEGStruct).

## Кто читает `+0x4c8`

Всего два потребителя, оба в том же kext.

### 1. Инициализатор/вайп — `0xfffffff008c8509c`

```
0x8c8518c  ldr  x8, [x19, #0x4c8]      ; ptr
0x8c85190  ldr  x10,[x19, #0x4d0]      ; count
0x8c85194  add  x9, x8, x10, lsl #2
0x8c851b4..0x8c851c8                   ; str wzr,[x8],#4 — цикл на count dword'ов
```

- Вайп ничего не пишет обратно в `+0x4c8/+0x4d0`: поля остаются как были.
- Для `count = 0x3df` цикл обнуляет `0x3df*4 = 0x37fc` байт.
- Все 5 call-site'ов инициализатора стоят **сразу после** `kalloc_type`
  (desc `0x7e2c498`), т.е. на свежем объекте:

| call-site | alloc перед ним |
|---|---|
| `0x8c85088` | `0x8c85078` (фабрика `0x8c8505c`) |
| `0x8c855c0` | `0x8c855a8` |
| `0x8c860cc` | `0x8c860b4` (startDecoderExt) |
| `0x8c868cc` | `0x8c868b8` |
| `0x8c870e0` | `0x8c870c8` (startDecoder2024) |

На свежей сессии `+0x4c8 == 0` (аллокатор zeroed — см. «не подтверждено»),
поэтому ветка вайпа не срабатывает. Повторного init'а живой сессии после
borrow в коде нет — вайп с непустым указателем недостижим.

### 2. copy-to-e8 — `0xfffffff008ca83b8`

```
0x8ca8500  add  x9, x19, #0x4c8
0x8ca8504  ldr  q0, [x9]          ; {ptr,count}
0x8ca8508  stur q0, [x19, #0xe8]  ; -> session+0xe8 / session+0xf0
```

Дальше декодер читает битстрим из `[session+0xe8]`. Вызов — из callback'а
`0x8c858fc`:

```
0x8c85e48  ldr  x0, [x20, #0x160]
0x8c85e4c  mov  x1, x19            ; x19 = session (x1 callback'а)
0x8c85e50  bl   0x8ca83a4
0x8ca83a8  ldr  w8, [x1, #0x2a8]
0x8ca83ac  cbz  w8, 0x8ca83b4
0x8ca83b4  b    0x8ca83b8          ; copy-to-e8
```

`[session+0x2a8]` зануляется в `0x8c86138` (Ext) / `0x8c8714c` (2024), так что
для обеих borrow-веток путь ведёт в `0x8ca83b8`.

Других чтений `+0x4c8` в образе нет: capstone-свип всего `__TEXT`/`__TEXT_EXEC`
JPEG (47 102 инструкции, 4 недекодируемых слова) даёт ровно 3 обращения к
полю (`0x8c8518c`, `0x8c8634c`, `0x8c87368`) плюс `add x9,x19,#0x4c8`
(`0x8ca8500`).

## Время жизни сессии

1. `kalloc_type(desc 0x7e2c498)` + init: `0x8c860b4 → 0x8c860cc` (Ext),
   `0x8c870c8 → 0x8c870e0` (2024).
2. Копирование полей входа в сессию (`0x8c860f4..0x8c86198` /
   `0x8c87108..0x8c871ac`), включая borrow-запись.
3. Синхронный вызов через `[driver+0xb8]`, vtable `+0xe8`:
   `0x8c864b0..0x8c864f8` (Ext) / `0x8c874f0..0x8c87530` (2024).
   Аргументы: `x1 = pacia(0x8c858fc, key 0xbd41)` — callback,
   `x2 = x21` — сессия, `x3=x4=x5=0`. Возврат (`x0`) сразу используется как
   статус (`0x8c864fc → cbz w23`), сессия сразу после этого уничтожается —
   это и есть признак синхронности.
4. Уничтожение: `0x8c8651c` (desc `0x7e2c598`) / `0x8c86560` (`0x7e2c558`)
   для Ext, `0x8c87554` (`0x7e2c718`) / `0x8c875f4` (`0x7e2c6d8`) для 2024.
   Дескрипторы отличаются от alloc-дескриптора на `0x100`/`0xc0` — та же
   пара «alloc/free view», что и у остальных типов kext'а
   (`0x198→0x298`, `0x1d8→0x2d8`, `0x218→0x318`, `0x258→0x358`).
5. Публикации сессии нет: ни одного `str x21/stp x21` в клиент/глобал.
   Единственная запись указателя на себя — `0x8c85d30: str x19,[x19,#0x80]`
   (self-pointer внутри той же сессии).

Callback `0x8c858fc` тоже не публикует сессию: все его non-stack store'ы идут
в `x19` (сессия), `x20` (объект gate'а) или в буферы, полученные из сессии.

`args+0x30` в этот момент — `structureInput` external method'а (kernel-копия,
владелец — IOUserClient, живёт до возврата из `externalMethod`). Диспетчер
пиннит точный размер входа (`0x1000` для Ext, `0xda0` для 2024 — по отчёту
subagent W), поэтому `[in+0x84 .. in+0x84+0x37fc]` не выходит за буфер:
`0x84+0xf7c = 0x1000`, `0x84+0xc00 = 0xc84`.

## Скан по всем сегментам и соседям (27.2)

Raw-скан всех `__TEXT_EXEC/__TEXT/__PRELINK_TEXT` с корректным масштабом
imm12 (для 32-bit форм `0x99*4 = 0x264`, а не `0x4c8`) даёт 1552 обращения
к смещению `+0x4c8` во всём образе. По kext'ам:

- `com.apple.driver.AppleJPEGDriver` — 4 (3 чтения/записи поля + 1 `add`);
- `com.apple.filesystems.apfs` — 702, `AppleCS42L77Audio` — 35,
  `AGXG14P` — 28, `AppleAVE2` — 20, `AppleARMPlatform` — 19,
  `AppleM2ScalerCSCDriver` — 12, `AppleH13CameraInterface` — 10,
  `AppleProResHW` — 7 и т.д. — это собственные структуры этих kext'ов;
  тип сессии JPEG (`kalloc_type 0x7e2c498`) приватен и никуда не экспортируется,
  так что кросс-kext потребителя быть не может.

27.0 / 24A437 содержит тот же код (сдвиг на `-0x36760`):

- `ldr x8,[x19,#0x4c8]` — `0xfffffff008c4ea2c`;
- `str x23,[x21,#0x4c8]` + count `0x3df` — `0xfffffff008c4fbec` / `0x8c4fbf0`;
- `str x23,[x21,#0x4c8]` + count `0x300` — `0xfffffff008c50c08` / `0x8c50c0c`;
- `add x23,x19,#0x84` — `0x8c4fbb0`, `0x8c50bc4`.

То есть ветка не новая в 27.2, а давняя; полный lifetime-анализ 27.0 не
перепроверялся (перенесён по совпадению кода).

## Что превратило бы латентность в рабочий UAF

1. Кэширование сессии в user client'е/драйвере между external method'ами
   (сейчас сессия per-call и уничтожается в той же функции).
2. Асинхронный `runAction`/очередь: callback `0x8c858fc` должен исполняться
   после возврата из `startDecoder` — тогда и `+0x4c8`, и сама сессия
   окажутся use-after-free.
3. Повторный вызов инициализатора `0x8c8509c` на живой сессии после borrow:
   вайп-цикл `0x8c851b4..0x8c851c8` обнулит `0x37fc` байт по указателю,
   который к тому моменту уже освобождён.

Ни одного из трёх в 27.0/27.2 нет.

## Не подтверждено

- Класс/метод `[driver+0xb8] + 0xe8`: символов нет; синхронность выведена из
  того, что возврат сразу трактуется как статус, а сессия уничтожается сразу
  после вызова (для async это был бы немедленный session-UAF).
- Identity стабов `0x8ca9278` (alloc) и `0x8ca9228` (dealloc): имена не
  разрешены; парность дескрипторов `+0x100` — косвенная.
- Zeroing аллокатора: принято, потому что инициализатор читает
  `+0x4c8/+0x4d0` **до** первой записи в них; при незированном alloc это был бы
  wild write на каждом вызове.
- Владелец `args+0x30` — MIG-copyin vs IOMemoryDescriptor: generic
  IOUserClient2022 не локализован (совпадает с выводом subagent W).
