# 27.2 / 24B115 — итог по kernel R/W

## 0. Вердикт

| Вопрос | Ответ |
|---|---|
| CVE-2026-112611 (Type 5 shading OOB write) на 24B115 | **закрыт**. Гейт стоит в RC-бинаре CoreGraphics; на 27.0/26.6 его нет |
| CVE-2026-112610 (CMap /UseCMap OOB write) на 24B115 | **закрыт**. `CG-SEC-187882136` + fallback на identity |
| «OOB write из репо» на этой сборке | **не существует**. Это не «сложно достать» — записи нет |
| Userland OOB write → kernel R/W | **невозможно напрямую**. Другая адресная область, другой привилегированный уровень. Нужен отдельный kernel-bug |
| Ядро устройства == ядро в Ghidra | **да**. 24B115 vs 24B119: 15 байт заголовка + 918 байт `__PRELINK_INFO`, **0 байт в кодовых сегментах** |
| SPTM 24B115 == 24B119 | **да**, sha256 `a681f086…`. TTBAT-исключение 27.0.1 **закрыто** (`VIOLATION_UAT_ILLEGAL_TTBAT_MAPPING`, `VIOLATION_UAT_ILLEGAL_TTBAT_LOCK`) |
| Публичный kernel R/W на 27.2 | нет. Calif-цепочка 27.0.1 закрыта в 27.2 |

Одна строка: на 27.2 kernel R/W — это **новый kernel-bug**, а не продолжение CG-бага. Всё, что можно было выжать из репо на этой сборке, выжато: баг мёртв.

## 1. Чем это доказано (не словами)

### 1.1. Устройство

`.ips` с самого телефона: `kaslr_probe-2026-10-27-113956.ips`

```
"os_version" : "iPhone OS 27.2 (24B115)"
"exception"  : EXC_BAD_ACCESS KERN_INVALID_ADDRESS at 0xffffffffffffffe8
```

То есть цель — **RC 24B115**, не 24B119.

### 1.2. CoreGraphics: гейт в RC-бинаре

`CoreGraphics.RC115`, `_CGPDFShadingType5Init` @ `0x183c5c88c`:

```
0x183c5caa8: ldr  x9, [x8, #0x30]   ; nc — число компонент colorspace
0x183c5caac: ldr  x8, [x20, #0x58]  ; /Function
0x183c5cab0: cbz  x8, #0x183c5cac8
0x183c5cab4: ldr  x10, [x8, #0x30]  ; range_dim функции
0x183c5cacc: cmp  x9, #4
0x183c5cad0: b.hi #0x183c5cb9c    ; nc > 4  -> reject
0x183c5cad4: cmp  x10, x9
0x183c5cad8: b.ne #0x183c5cb9c    ; range != nc -> reject
```

Строки в бинаре:

```
CoreGraphics.RC115 : CG-SEC-187882049 + CG-SEC-187882136   есть
CoreGraphics.27.2  : CG-SEC-187882049 + CG-SEC-187882136   есть
CoreGraphics.27.0  : нет
CoreGraphics.26.6  : нет
```

`_cg_shading_type5_draw` в 27.2 **побайтово тот же**, что в 27.0 (фикс только в init). Значит, обойти гейт через draw нельзя: до draw такой shading просто не создаётся. Type 4 имеет свою проверку `range == nc` и `nc+1 <= 5` в draw; Type 6/7 с функцией до eval не доходят. Соседних незакрытых путей в shading нет.

### 1.3. Ядро: RC == release по коду

Из OTA 24B115 вытащен настоящий kernelcache (не 24B119):

```
work/rc115/24B115__iPhone14,7/kernelcache.release.iphone14b   67 239 936 B
@(#)VERSION: Darwin Kernel Version 27.2.0: Tue Oct 13 21:26:30 PDT 2026
             root:xnu-13432.42.3~28/RELEASE_ARM64_T8110
```

Сравнение с `work/kc272/24B119__iPhone14,7/kernelcache.release.iPhone14,7`:

```
различий: 933 байта
  __TEXT (Mach-O header)  :  15
  __PRELINK_INFO          : 918
  __TEXT_EXEC / __TEXT    :   0   <- кода нет
```

Вывод: **Ghidra-проект `kernelcache.release.iphone14b.decompressed` — это ровно то ядро, что на телефоне.** Все адреса из отчётов применимы к 24B115.

### 1.4. SPTM: TTBAT-дыра закрыта

`work/rc115/.../sptm.t8110.release.im4p` == `work/sptm_27.2_24B119.im4p` (побайтово, sha256 `a681f086b6e765787e663214d879f53ca6319afa2fcea37495e90050eddd3818`).

В 27.2 SPTM есть строки, которых не было в 27.0.1:

```
VIOLATION_UAT_ILLEGAL_TTBAT_MAPPING
VIOLATION_UAT_ILLEGAL_TTBAT_LOCK
```

То есть исключение «PA == gpu-region-base → пропустить проверку прав», которое в 27.0.1 давало writable-маппинг TTBAT, в 27.2 обложено violation-проверками. Путь «TTBAT → GPU page tables → физическая память» на 27.2 не работает. Это независимо подтверждает, что Calif-цепочка 27.0.1 в 27.2 закрыта.

## 2. Почему userland OOB не даёт kernel R/W

CG-баг — это запись в **malloc-кучу процесса-рендерера**. Даже если бы он был жив:

* адрес записи — user VA, не kernel VA;
* привилегии — sandboxed app/рендерер, не EL1;
* максимум — RCE в этом процессе, дальше sandbox escape и отдельный kernel-bug.

Цепочка «PDF → kernel R/W» в любом случае состоит из трёх разных багов: **рендерер → sandbox escape → kernel**. Один OOB write не заменяет второй и третий. На 27.2 первого бага тоже нет.

## 5. Куда идти дальше (по приоритету)

1. **Не искать OOB в CG 27.2.** Он закрыт. Любая работа по PDF на этой сборке — впустую.
2. **Новый kernel-bug.** Рабочие зоны, где есть userland-ввод и сложная арифметика:
   - `IOSurface` HTPC — потребитель геометрии (VideoToolbox / IOMFB), а не сам валидатор;
   - `AppleJPEGDriver` — внутренний кодек (`FUN_…8c86bd4`, `FUN_…8c876d8`), не IOKit-обёртки;
   - `AGXG14P` / `IOGPUFamily` — command buffers, GMMU, TTBAT-потребитель;
   - `AppleT8110DART` — обновлён в 27.2, SID/TTBR-shadow;
   - `apfs` — обновлён в 27.2, userland-достижим.
3. **Метод**: diff 27.2 vs 27.0.1 искать не «что починили» (это мёртвое), а **новый код** — новую поверхность. HTPC-поля — как раз такой новый код; следующий шаг — не валидатор, а его потребители.
4. **KASLR**: без утечки kernel text slide любой kernel-bug половинчат. Проверять `IOSurface` sel 0/3 (`0xc68`), `IOGPU` sel 2 (`0x218`), AppleJPEG sel 4/6 — на неинициализированный хвост. В 27.2 in-band output инициализируется пользователем, поэтому искать нужно **copyout из kernel-буфера** (OOL/`structureOutputDescriptor`), а не in-band.
5. **Устройство**: пока locked, USB-данные не идут (`ideviceinfo` — no device). Когда разблокируешь — снять `iosurface`-пробы и `kaslr_probe`.

## 6. Честная граница

- Проверено статикой по **точному** бинарю устройства: gate в CG, идентичность ядра, SPTM TTBAT closure, entitlement на IOSurface-указатель.
- Не проверено запуском: HTPC-потребители, IOSurface sel 24 на реальном MIG-пути, work-token heap grooming. Для этого нужен разблокированный телефон.
- Arbitrary kernel R/W на 27.2 **не получен**. Причина не в том, что «не искали»: на этой сборке репо-примитив отсутствует, а найденные живые лиды либо закрыты entitlement'ом, либо не дают контроля. Это отдельная исследовательская работа — новый kernel-bug, не продолжение CVE-2026-112611.
