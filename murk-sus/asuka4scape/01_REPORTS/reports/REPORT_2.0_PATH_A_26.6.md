# REPORT 2.0 — 26.6.1 ветка (PATH A) + ROUTE/NECP проба

Дата: 01.11.2026. Компаньоны: `REPORT_1.9_SELSCAN_GATES.md`, `KCORE_FIX_AUDIT.md` (F1/F3),
`发现汇总_理论内核RW_中文.md` (путь A). Артефакт: `probe/out/KRWProbe.ipa` 2.0 (build 20).

## 0. Вердикт

**На 26.6.x (23G71/23G82/23G90, xnu-12377.162.14) оба компонента PATH A ожидаются живыми:**
CVE-2026-112507 (rt_setgate, OOB write) и CVE-2026-112665 (NECP/CFIL, KASLR leak) —
фиксы легли в 26.7.2 + 27.2, 26.6.x их не содержит. Статическое подтверждение по
23G71-кэксту: assertion `sdl->sdl_alen == size` присутствует (в 27.2 удалён фиксом),
фикс-shaped reject-сообщения отсутствуют. Ядро 26.6.1 (23G82) — та же ветка 12377.
Проба 2.0 проверяет это на устройстве и измеряет достижимость из песочницы.

## 3. KRWProbe 2.0 — что добавлено

- **ROUTE 26.6** (`route_loop`, `route.txt`):
  1. `socket(PF_ROUTE, SOCK_RAW)` — сам по себе тест достижимости сэндбокса.
  2. Три RTM_ADD с AF_LINK-шлюзом, где `sdl_alen` врёт против `sdl_len=16`:
     L0 control alen=6 → L1 alen=32 → L2 alen=0xf7 (уровень ограничен файлом
     `KRWProbe-route.txt`: `max_level=2`, по умолчанию 1).
  3. На каждый успешный ADD: RTM_GET (что ядро сохранило) + RTM_DELETE (уборка).
     Ответы дампятся и сканируются на kernel-указатели.
- **NECP** (`necp_open` SYS 501 / `necp_client_action` SYS 502 на 26.6):
  открытие клиента, минимальный ADD, connect() под клиентом. Достижимость.
- IPA: `probe/out/KRWProbe.ipa`, 120 689 B, sha256 `a739bc33…d8c9`, версия 2.0/20.

### Как читать результат ROUTE

| симптом | вывод |
|---|---|
| `socket(PF_ROUTE) = -1 EPERM` | сэндбокс закрывает route-сокеты из приложения — PATH A нужен другой вход (NECP/NX или хелпер-процесс) |
| L1/L2: reply errno != 0 | ядро **заплатано** — шлюз отвергнут (форма фикса 27.2) |
| L1/L2: errno=0, RTM_GET показывает gateway с alen=32/0xf7 | **уязвимость жива**: rt_setgate принял ложный шлюз; дальше — выбор пишущего потребителя (arp/nd6/if_llreach) |

## 4. Честная граница / открытые вопросы PATH A

1. **Канал чтения DATA-TRACE**: печать `<so %llx>` уходит в kernel os_log — приложение
   не читает ядерный лог напрямую. Слайд из 112665 вытягивается либо sysdiagnose'ом
   после кнопки (ручной цикл, слайд живёт до ребута), либо нужна замена:
   OOB-read-потребитель route-данных (RTM_GET копирует наружу ровно сохранённые
   байты — сам по себе утечки не даёт; смотри arp/nd6 конвертацию шлюза).
2. **Пишущий потребитель**: acceptance теста доказывает баг, но не примитив.
   Кандидаты из аудита: arp/nd6/if_llreach/rtsock — следующий статический шаг
   после подтверждения acceptance.
3. **PF_ROUTE из песочницы** — неизвестно до прогона; это и есть главный вопрос
   кнопки ROUTE.
4. Ядро для 23G82 (26.6.1) — точный билд: пока работаем от 23G71; для
   слайд-калькуляции понадобится расшифрованный кэкст 23G82 (есть путь через
   тот же `ipsw kernel dec`).
