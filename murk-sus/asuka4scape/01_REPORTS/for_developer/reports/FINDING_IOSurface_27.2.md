# CVE-2026-112477 — точное место фикса в iOS 27.2 (IOSurface race)

Дата: 28.10.2026. Бинарный дифф `com.apple.iokit.IOSurface` 27.0 (24A437) ↔ 27.2 (24B115),
секция `__text` (53 639 ↔ 53 645 инструкций, shape-diff).

## Результат

Весь фикс — **6 инструкций в трёх функциях**:

| 27.0 | 27.2 | что добавлено |
|---|---|---|
| `FUN_fffffff009bf9900` | `FUN_fffffff009c35890` | `ldrb; tbz` + ветка `add; b` |
| `FUN_fffffff009bf9b60` | `FUN_fffffff009c35ae0` | `mov #1; strb` |
| `FUN_fffffff009bfead4` | `FUN_fffffff009c3aa7c` | `strb` + `bl` |

Остальные 53 633 инструкции совпадают по форме (ratio 0.99985). Значит патч точечный.

## Что именно изменилось

### 1. `IOSurface::addChild` (27.2: `FUN_0x9c35850`, вызывается из `FUN_0x9c3d338`)

```c
lock(surface->lock_150);
if ((*(u8*)(child + 0xf1) & 1) == 0) {          // флаг «ребёнок умирает»
    ... поиск дубликата по (child, client) в списке surface+0x188 ...
    ... вставка новой записи ...
} else {
    ret = 0xe00002d8;                            // kIOReturnNotReady
}
unlock(surface->lock_150);
```

### 2. `IOSurface::removeChild` (27.2: `FUN_0x9c35ad4`)

```c
lock(surface->lock_150);
*(u8*)(child + 0xf1) = 1;                        // <-- ДОБАВЛЕНО В 27.2
... обход списка surface+0x188, удаление записи child, free(entry) ...
unlock(...);
```

### 3. `FUN_0x9c3aa54` — тот же паттерн (флаг + вызов) на втором пути.

## Модель уязвимости

`child+0xf1` — флаг «объект в процессе уничтожения». В 27.0 он **проверялся** в add-пути,
но **никем не выставлялся** (единственные две функции, трогающие `+0xf1` во всём кексте —
add и remove; в 27.0 `strb` в remove отсутствует).

Следствие: `removeChild` снимает ребёнка со списка и освобождает запись, но не помечает
сам IOSurface-объект. Поток, который уже держит указатель на ребёнка (например, получил его
из списка/кэша без refcount), может после destroy вызвать `addChild` и вставить в список
повторно уже освобождённый объект → висячая ссылка в `surface+0x188` → UAF при следующем
обходе (map/unmap/lock ребёнка). Это ровно формулировка бюллетеня: race condition,
improved locking, «corrupt kernel memory».

## Статус на 27.2

Фикс присутствует: флаг ставится под тем же локом (`surface+0x150`), который держит add-путь,
и `addChild` после destroy возвращает `0xe00002d8`.

Во всём кексте `+0xf1` трогают только эти две функции — другого пути освобождения ребёнка,
который не выставил бы флаг, в 27.2 нет.

**Вывод: примитива здесь нет.** Ранее сделанный вывод «кекс не менялся» был артефактом
сравнения первого сегмента (`__TEXT`) вместо секции `__text` — исправлено.

## Что осталось проверить (siblings)

- Освобождение **родителя** при живых детях: очищается ли `child+0xe8` (указатель на родителя)
  в free-пути родителя. Если нет — обратная висячая ссылка (ребёнок → родитель).
- `IOSurfaceDeviceCache` / `IOSurfaceMemoryPool`: те же списки (`+0x188`) с другими типами.
