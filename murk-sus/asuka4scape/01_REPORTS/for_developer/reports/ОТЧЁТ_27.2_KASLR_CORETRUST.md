## 2. KASLR: что проверено и закрыто

### 2.1 `mach_port_kobject` — редактирован
27.2, MIG stub `0xfffffff00a2a45b8` → сервер `0xfffffff00a1ff4f8`.
Ключевые инструкции:

```
0xfffffff00a1ff5ac  str  w8, [x22]      ; x22 = reply+0xc  (type)
0xfffffff00a1ff5d8  str  xzr, [x21]     ; x21 = reply+0x10 (kobject) == 0
```

То есть kobject всегда 0; остаётся только type/описание. Утечки нет.

### 2.2 `mach_port_space_info` — поля занулены
27.2 stub `0xfffffff00a2a4a3c` → сервер `0xfffffff00a1feb98` (ветка space/UPL).
Внутри: `str xzr,[x21]`, `str wzr,[x19]` — указательные поля reply обнуляются до
заполнения. Классический leak `iis_table_addr`/`itn_object` закрыт.

### 2.3 `thread_info` — только user VA
`FUN_0xa273d34` (flavor dispatch):
- flavor 4 (THREAD_IDENTIFIER_INFO): `*param_9 = thread->thread_id; param_9[1] = thread_handle;`
  `dispatch_qaddr = thread_handle + per-task base` — это **user**-адрес очереди
  libdispatch, не kernel.
- flavor 5 (EXTENDED): времена/приоритеты, указателей нет.
- flavor 10/11: timeshare, указателей нет.

### 2.4 IOSurface bulk attachments — не течёт
Селектор 2/6 (output 0xc68) → `FUN_0x9c3b3ac` → `FUN_0x9c2c18c`.
В `FUN_0x9c2c18c` перед заполнением:

```
0x...  thunk_FUN_fffffff00aa65cc0(param_8, 0xc68)   ; bzero(output, 0xc68)
```

Дальше поля копируются из объекта surface; неинициализированного хвоста нет.

### 2.5 Новые syscall'ы 27.2 — чисто
Diff 26.6 ↔ 27.2: новых номеров нет; восемь слотов `nosys` стали живыми:
`pipe2(148)`, `dup3(149)`, `fchflagsat(214)`, `getumask(215)`,
`aio_readv(246)`, `aio_writev(247)`, `fsctlat(249)`, `guarded_ftruncate_np(352)`.

Разобраны:
- `guarded_ftruncate_np` (`0xa6f9560`): copyin 8 байт guard в локаль, проверка
  длины ≤ file size, вызов `0xa407178`; утечки нет.
- `aio_readv/writev` (`0xa6e473c`/`0xa6e5260` → `0xa6e3bd0` → `0xa6e3df8`):
  aiocb копируется в локальный буфер, **буфер предварительно занулён**, iovcnt
  ограничен `DAT_fffffff00ad18808`; утечки нет.
- `pipe2`/`dup3`/`fchflagsat`/`getumask`/`fsctlat`: обёртки без copyout
  неинициализированных структур.

### 2.6 Что остаётся для KASLR
- IOAccelerator/AGX shared memory: статически не проверено до конца; это
  единственный класс, где исторически лежали kernel pointers в user-mapped
  странице. Нужен разбор `AGXDeviceUserClient` shared page и IOGPUDevice
  shared memory (см. `kaslr/iokit/dumps/cpp_all.txt` — инвентарь классов).
- `IOSurfaceRootUserClient` selector 0 (`0x9c3888c`) мапит shmem клиента и
  передаёт его в `0x9c3ab8c`; проверить, не копирует ли он поля ядра в output.
- Динамический скан на устройстве: любой API, вернувший qword с топ-байтами
  `0xfffffff0..0xffffffff`, — кандидат. Готовый probe: `kaslr_probe/` (см. §5).

## 3. CoreTrust: где логика и что она проверяет

### 3.1 Карта kext'а (27.2, VA)

| Функция | Роль |
|---|---|
| `0x94c82cc` | построение цепочки (issuer/subject) + **проверка корня** |
| `0x94c84c4` | поиск сертификата в таблице pinned (store #1, count `0x77705c9`) |
| `0x94c8580` | поиск в таблице pinned (store #2, count `0x777164a`) |
| `0x94c8c04` | классификация по **subject-строке** (CA name table `0x7f5b3c0..`) → flags |
| `0x94c8d1c` | policy-flags по сертификату/таблице `0x7f5abb0` |
| `0x94c8638` | основной проход по цепочке: поля, OID, подпись, финальные flags |
| `0x94c6bf4` | DER-парсер (BIT/OCTET STRING, длины с CARRY8-проверками) |
| `0x94c6eac`, `0x94c71b0` | OID → policy (`FUN_94c3158/3364/3658`), проверка extension OID |
| `0x94c70e8` | verify подписи (внешняя crypto-функция) |
| таблицы | `0x7f5aa70`, `0x7f5b3c0`, `0x7f5ae38`, `0x7f5b8b8` |

Строки CA: `Apple iPhone Certification Authority`,
`Apple Code Signing Certification Authority`, `Apple Accessories ...`,
`Apple Accessory Host Attestation Authority` — лежат в `__TEXT.__const`
(`0x76d184..`), таблица `{ptr,len}` — в `__DATA_CONST` (`0x7f5b3c0..`).

### 3.2 Найденная логическая развилка (кандидат на байпас)

`FUN_0x94c82cc` строит цепочку и на корне делает:

```c
lVar10 = FUN_94c84c4(uVar2, 1);          // pinned store #1
if (lVar10 != 0) return 0;               // точное совпадение сертификата
lVar10 = FUN_94c8580(uVar2);             // pinned store #2
uVar3 = 0;
if (param_4 == 0) uVar3 = 0x80008;       // <-- корень НЕ pinned => ошибка только если param_4 == 0
if (lVar10 != 0) uVar3 = 0;
return uVar3;
```

Смысл: при `param_4 != 0` **непиннутый (самоподписанный) корень принимается**
(возврат 0). Вызов из `FUN_0x94c264c`:

```c
uVar4 = FUN_94c82cc(plVar5, &local_538, &local_548, param_4 ^ 1);
```

То есть непиннутый корень проходит, когда у `FUN_94c264c` **бит0 `param_4` == 0**.
`param_4` — флаги policy, приходящие от вызывающего (AMFI), не из подписанного
CMS напрямую. Вопрос, который решает байпас: может ли пользователь выбрать policy
с этим битом (тип trust cache / тип подписи / профиль), и не пиннится ли корень
на другом уровне (`FUN_94c8638` для anchor'а вызывает `FUN_94c84c4` при
`param_4[2] & 1 != 0`).

Проверка на устройстве: собрать цепочку `leaf(self-signed) -> intermediate(fake,
subject как у Apple CA) -> root(self-signed)`, подписать CMS своим ключом,
поставить в профиль/подпись и посмотреть, доходит ли до `0x80008` или до успеха.
Если доходит до успеха при определённом policy — это и есть CoreTrust bypass.

**Важное уточнение после трассировки вызывающих.** `param_4` в `94c264c` — это
не пользовательский ввод, а константа конкретной policy-обёртки:

| Обёртка | `param_4` в `94c264c` | `param_4 ^ 1` в `94c82cc` | корень |
|---|---|---|---|
| `FUN_94bee68` | 1 | 0 | только pinned |
| `FUN_94beeb4` | 1 | 0 | только pinned |
| `FUN_94bf004`, `94bf14c`, `94bf1ec` | 1 | 0 | только pinned |
| **`FUN_94c2bd8`** | **0** | **1** | **непиннутый принимается** |
| `FUN_94c2e68` | 0 | 1 | непиннутый принимается |

То есть «дыра» — это отдельная policy-ветка (`FUN_94c2bd8` / `FUN_94c2e68`),
которая использует policy-таблицы `0x7f5ad68` и `0x7f5b8d0` (вероятно,
local/development-подпись). Она действительно принимает самоподписанный корень,
но вопрос эксплуатации — какие flags она возвращает в `param_5` и достаточно ли их
AMFI для `platform-application`/`can-load-trust-cache`. Это надо проверять на
устройстве; без этого называть её bypass'ом нельзя.

### 3.3 Что ещё проверяет основной проход
- `uVar12+0x10a & 1` → ошибка `0x90007` (запрещённый флаг сертификата);
- `FUN_94c519c(uVar12+0x28, uVar12+0x98)` → `0x90004` (несовпадение полей);
- `param_4[1]` — маска обязательных flags; `(flags & mask) == 0` → `0x90005`;
- `FUN_94c70e8` — verify подписи; ошибка → `0x9000e`;
- anchor: `FUN_94c84c4(anchor, bit)` → `0x9000b`, если не pinned (при `param_4[2]&1`).

## 4. AMFI / TrollStore-путь (что нужно после байпаса)

`AppleMobileFileIntegrityUserClient` (27.2) — методы:

| Метод | Что делает | Entitlement |
|---|---|---|
| `setDenylist` | запись denylist | `...can-set-denylist` (строка `0x7634dee`) |
| `loadTrustCache` | загрузка trust cache из input | `com.apple.private.amfi.can-load-trust-cache` (`0x763515e`) |
| `loadCompilationServiceCodeDirectoryHash` | cdhash в compilation-service TC | `com.apple.private.amfi.can-load-cdhash` (`0x76352ed`) |
| `isCdhashInTrustCache` | проверка cdhash | `com.apple.private.amfi.can-execute-cdhash` (`0x7636113`) |

То есть после получения entitlement'а (`platform-application` или
`can-load-trust-cache`) приложение может само загрузить trust cache с нужными
cdhash'ами — это и есть «AMFI выключен для наших приложений» по модели TrollStore.
Формат TC-блоба и `copyTrustCacheAndManifestFromInputArgument` — следующий объект
разбора (строки `0x7634f81..0x7635236`).

## 6. Честная граница

- KASLR: в проверенном корпусе (MIG/IOKit/syscall/новые вызовы) kernel-text
  утечки нет; остаются AGX/IOGPU shared memory и динамический probe.
- CoreTrust: найден конкретный условный путь принятия непиннутого корня; чтобы
  назвать это эксплойтом, нужно доказать контроль policy-флага и собрать
  цепочку, которую примет AMFI. Без устройства это не проверяется.
- SPTM TTBAT (820.40.24) жив: `FUN_0x270adf30`, `out_pa == SK[0x68]` →
  проверка прав `0x270e1168` пропускается; нужен вызов UAT MAP_BEGIN с PA =
  `gpu-region-base`, то есть kernel-примитив с контролем PA.
