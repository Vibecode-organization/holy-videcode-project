# UAF / гонки жизненного цикла — IOGPUDeviceUserClient + AGXCommandQueue
**Прошивка:** iOS 27.2 (24B115) · `27.2_24B115_kernelcache` (67 239 936 байт)
**Профиль:** `container`, без `com.apple.developer.gpu-restricted` → доступна полная таблица A из 56 селекторов.
**Автор:** subagent O. Метод — статический разбор (capstone 5.0.7), скрипты в `kc.py` / `bl.py` / `xr.py`.

Все адреса — VA. `__TEXT_EXEC` = `va - 0xfffffff007004000`; `__DATA_CONST` = `0xbb4000 + (va - 0xfffffff007bb8000)`.
PAC-резолв указателей из таблиц: `BASE + (q & 0x0FFFFFFF)`, `BASE = 0xfffffff007004000`.
В capstone `adrp`/`b`/`bl` знаковые — во всех скриптах маска `& 0xFFFFFFFFFFFFFFFF`.

---

## 0. Короткий ответ

**UAF в пути «id → объект» не найден.** Модель ровно та, которую требует корректный дизайн:
`IOGPUNamespace` защищён спящим мьютексом `[ns+0x20]`, `retain` берётся **под тем же мьютексом**,
что и `remove`, слот обнуляется **до** возврата указателя, финальный `release` всегда идёт **после** `unlock`.
Классика «`delete(id)` параллельно с `submit/use(id)`» не срабатывает: поток-пользователь либо получает
валидный объект с +1 к `gpu_refcnt`, либо получает NULL.

Одна оговорка: 12 из 17 вызовов `lookupRaw` (`0x9945214`) доказанно под локом; ещё 5 — виртуальные
thunk-и, чьи вызывающие статически не резолвятся. Это **единственное** непокрытое место модели,
вынесено в §6.

Что **реально** нашлось (все три — не memory-safety, но живые):

| # | Дефект | Тип | Подтверждено |
|---|---|---|---|
| 1 | `s_new_command_queue`: лимит очередей читается вне лока → TOCTOU, лимит обходится числом потоков | гонка счётчика | **да** (дизасм + отсутствие лока) |
| 2 | `s_delete_command_queue`/`s_destroy_io_command_queue`: `remove()` + освобождение **вне** лока при уже освобождённом id → окно переиспользования id | окно, не UAF | **да** как окно, **нет** как UAF |
| 3 | `s_new_resource`/sel 9: удаление ресурса вызывает только `[res vt+0xb0](res, dev)` и **не вызывает `release`** — в отличие от всех остальных путей удаления | утечка `gpu_refcnt` | **частично** (release на пути нет; что делает `vt+0xb0` — не подтверждено) |

Плюс отдельно: `[uc+0x11c]` (`ldadd`) инкрементируется до создания объекта и **не откатывается** на error-ветках
(`0x9947830`→`0x99478c8`, `0x994787c`→`0x9947954`) — счётчик «созданных очередей» растёт от неудачных попыток.

Строки ядра подтверждают классы (все в `__PRELINK_TEXT`):
`'IOGPUNamespace.cpp'` `0x782ad6a`, `'site.IOGPUNamespace'` `0x782ad8c`, `'IOGPUWeakNamespace'` `0x782ace9`,
`'site.IOGPUObject'` `0x782c0e8`, `'IOGPUObject.cpp'` `0x782c0fc`,

| VA | что делает | лок |

## 4. Топ-3: дизасм и точные последовательности

### 4.1 Гонка №1 — TOCTOU лимита очередей (подтверждено)

`s_new_command_queue`, `0xfffffff0099476bc`. Проверка лимита **не** под мьютексом namespace:

```
0x99476ec  ldr  x8, [x0, #0x120]      ; IOGPUDevice
0x99476f0  ldr  x8, [x8, #0x88]       ; ns очередей
0x99476f4  ldr  w8, [x8, #0x30]       ; ns->count   <<< ЧТЕНИЕ БЕЗ ЛОКА
0x99476f8  ldr  x0, [x0, #0xf8]
0x99476fc  ldr  w9, [x0, #0x248]      ; лимит
0x9947700  cmp  w8, w9
0x9947704  b.ls 0x9947750             ; не превышен -> идём дальше
...
0x9947870  ldr  x0, [x8, #0x88]
0x9947874  mov  x1, x21
0x9947878  bl   0x9944fb0             ; add() -> id (внутри лок)
```

Два потока:

```
T1: sel6(id=A)                        T2: sel6(id=B)
    0x99476f4  w8 = count = N-1            0x99476f4  w8 = count = N-1
    0x9947700  N-1 < limit -> ok           0x9947700  N-1 < limit -> ok
    ... create A ...                        ... create B ...
    0x9947878  add -> count = N             0x9947878  add -> count = N+1
```

**Итог:** `ns->count` может превысить `[dev+0x248]` на число одновременных создателей.
Проверка `cmp w8, w9` и вставка разнесены на ~0x180 байт и на две разные критиче­ские секции.
Последствие — обход лимита очередей (ресурсный DoS-барьер), не память.
Отдельно: `ldadd` на `[uc+0x11c]` (`0x9947764`) делается **до** создания и не откатывается
на `0x99478c8` / `0x9947900` / `0x9947954`; уменьшение есть только в sel 7 (`0x9947a00`, `w1=#-1`).

### 4.2 Гонка №2 — окно переиспользования id при удалении (окно есть, UAF нет)

`s_delete_command_queue`, `0xfffffff0099479c0`:

```
0x99479dc  ldr  x8, [x2, #0x20]        ; args->scalarInput
0x99479e0  ldr  w20, [x8]              ; id
0x99479e4  ldr  x8, [x0, #0x120]       ; device
0x99479e8  ldr  x0, [x8, #0x88]        ; ns очередей
0x99479f0  bl   0x9945154              ; removeLocked: слот=NULL, unlock, вернуть obj
0x99479f4  cbz  x0, err
0x99479f8  bl   0x997684c              ; ВНЕ лока: terminate + [obj vt+0x28]
```

`0x9945154` = `lock` → `0x994508c` (там `str xzr,[slot]` — слот обнуляется **до** возврата) → `unlock`.
Между `unlock` и `0x997684c` слот уже свободен и его может занять новый объект:

```
T1: delete(id=5)                      T2: new_command_queue
    lock
    slot[5] := NULL
    low-water := 5
    unlock
    --------- окно ---------            lock
                                        вставка видит свободный бит 5
                                        slot[5] := B ; count++
                                        unlock ; id = 5
    release(A)                          ...
```

**Почему это не UAF:** любой пользователь, зашедший в окно, получает либо NULL (если успел до
вставки), либо **B с +1** (если после). Ссылка на A, взятая *до* `remove`, держит `gpu_refcnt ≥ 2`,
поэтому `release(A)` в T1 её не убивает. Единственное последствие — семантический алиасинг:
клиент, считающий «id 5 = A», после переиспользования работает с B. Память не портится.

**Что проверялось и оказалось корректным:** `0x9944fb8` (`retain`) читает слот и делает `ldadd`
двумя инструкциями без лока — но **единственный** вызывающий `0x9945040` держит `[ns+0x20]`,
а `remove` (`0x9945154`, `0x99451a0`) берёт тот же мьютекс. Гонки «прочитал слот → объект освободили →
`ldadd` в освобождённую память» нет.

### 4.3 Гонка №3 — удаление ресурса без `release` (утечка `gpu_refcnt`)

`sel 9` → `0xfffffff009965954(device, id)`:

```
0x9965968  mov  x19, x0                ; device
0x996596c  ldr  x0, [x0, #0x10]        ; ns ресурсов
0x9965970  bl   0x9945154              ; removeLocked -> obj  (ref таблицы перешёл к нам)
0x9965974  cbz  x0, err
0x9965978  ldr  x16, [x0]              ; vtable
0x9965988  ldr  x8, [x16, #0xb0]!      ; vt+0xb0
0x996598c  mov  x1, x19                ; device
0x9965994  blraa x8, x16               ; obj->vt[0xb0](obj, device)
0x9965998  mov  w0, #0
0x996599c  b    epilogue               ; <-- release НЕТ
```

Сравнение с остальными путями удаления из `[dev+0x10]`:

| путь | remove | освобождение ссылки |
|---|---|---|
| `9965954` (sel 9) | `9945154` | **`vt+0xb0` — и всё** |
| `99654c4` (teardown) | `994508c` | `vt+0xb0` |
| `9963d0` (sel 7, `+0x88`) | `9945154` | `997684c` → `[vt+0x88]` + `[vt+0x28]` |
| `9963894c` (sel 43, `+0x110`) | `9945154` | `995b020` |
| `99451a0` (общий) | `994508c` | `[vt+0x28]` явно |

То есть для `[dev+0x10]` Apple использует `vt+0xb0` вместо явного `release`. **Что делает `vt+0xb0` —
статически не подтверждено** (vtable `IOGPUResource` в образе не лежит как массив PAC-указателей, которые
резолвятся формулой `BASE + (q & 0x0FFFFFFF)`). Если `vt+0xb0` не делает `release`, то:

```
T1: sel9(id=5) x N раз  ->  gpu_refcnt(A) += N (объект не умирает)
                            ns->count уменьшается корректно
```
Последствие — неубиваемые `IOGPUResource`, рост `gpu_refcnt` до `0x0FFFFFFF`, затем
`panic("gpu_refcnt: overflow (rc=%p)")` из `0x9983678`. Это DoS, не UAF.
**Помечено как «не подтверждено».**

## 5. Что проверено и признано корректным (важно для отчёта)

1. **Слот обнуляется при удалении.** `0x994508c`: `ldr x8,[x10]` → `str xzr,[x10]` → сброс бита → `count--`.
   Возврат `0` если слот уже пуст (`cbz x8, 0x994514c`). Двойного remove нет.
2. **Повторная проверка после лока.** Из 17 вызовов `0x9945214` (`lookupRaw`) **12 доказанно находятся
   внутри критической секции** `[ns+0x20]` — лок-вызов предшествует сайту в том же теле функции:
   `0x995b10c, 0x99652a4, 0x99652ec, 0x996537c, 0x99653d0, 0x9965570, 0x996567c, 0x99656c4,
   0x9965710, 0x996637c, 0x9966420, 0x9967c08`.
   Остальные **5 — thunk-и** вида `ldr x0,[x0,#imm]; b 0x9945214`, лока в теле нет:
   `0x9965624` (`[x0+0x10]` — ресурсы), `0x9965b54` (`+0x78`), `0x9965c90` (`+0x18`),
   `0x9965cc0` (`+0x100`), `0x9965f2c` (`+0x80`). Это виртуальные «getObjectNoRetain»;
   их вызывающие через vtable статически не резолвятся (см. §6) — **лок у них не подтверждён**.
3. **`+0xc` не «остаётся живым после освобождения таблицы».** `IOGPUNamespace` **не владеет** ссылкой:
   создатель передаёт свой `+1` в слот, `remove` отдаёт его обратно вызывающему. Поэтому таблица,
   умирая, дренируется циклом `remove+destroy` (`0x995b0c8` для `[q+0x38]`, `0x9965338` для `[dev+0x110]`
   / `[dev+0x88]` / `[dev+0x10]`). Висячих ссылок после освобождения таблицы не остаётся.
4. **`s_group_add_resources` корректно ретинит каждый ресурс** (`0x9967c20` → `[vt+0x20]`) **под локом
   namespace**, а на ошибке освобождает уже взятые (`0x9967ca4` → `[vt+0x28]` + обнуление слота).
5. **`s_group_remove_resources`**: per-group hash-таблица защищена своим мьютексом `[grp+0x60]`
   (`0x998428c`/`0x99842cc`), per-entry refcount `[entry+8]` меняется неатомарно, но под этим локом;
   при обнулении — `[obj vt+0x28]` и зануление `[entry]`.
6. **`s_submit_command_buffers`** держит `+1` на очередь всё время вызова (retain `0x9947f24`,
   release `0x9947f88`), id резолвится под локом. Классический сценарий из задания **не срабатывает**.
7. **`0x9944f7c`/`0x996fdf4`** — идиома «положить в массив, потом retain»; вызывается только из-под
   лока namespace, а массовый release (`0x996fe94`) работает по массиву, собранному тем же потоком.

## 6. Явно НЕ подтверждено

| Утверждение | Почему не подтверждено |
|---|---|
| `vt+0xb0` освобождает ссылку | vtable `IOGPUResource` не найдена в образе как массив резолвимых PAC-указателей; `pacda` в диапазоне IOGPU отсутствует |
| `AGXCommandQueue` (sizeof 0x948) достижима из таблицы `0x7fea200` | таблица ведёт только в `IOGPUCommandQueue` (`[dev+0x88]`); `AGXCommandQueue` создаётся через `[dev vt+0x698]` внутри `0x99669e0`-семейства и принадлежит AGXAccelerator. Прямого селектора к ней в 56 записях нет |
| `AGXCommandQueue` submit vs destroy | вне достижимости таблицы; отдельный userclient (`AGXDeviceUserClient`, 0x138) требует отдельного разбора |
| `9976cf8` (submit) синхронен | не проверялось; если он ставит работу в очередь асинхронно и работа переживает `release` в `0x9947f88` — это была бы UAF. Косвенно: релиз стоит сразу после возврата, что для асинхронного сабмита было бы ошибкой; на практике IOGPUCommandQueue::submitCommandBuffer ретинит дескрипторы сам |
| 5 thunk-ов `0x9965624/0x9965b54/0x9965c90/0x9965cc0/0x9965f2c` вызываются только под локом | это виртуальные методы; в образе они не встречаются ни как цель `bl`, ни как data-слот с резолвом `BASE+(q&0x0FFFFFFF)`. Если какой-то путь дёргает их **без** `[ns+0x20]`, то `lookupRaw` отдаст указатель без ref и без лока → классическая UAF. Это единственное непокрытое место в модели |
| Влияние `vt+0xb0`-утечки на реальный крах | требует динамики (паника на `0x0FFFFFFF` = 268 млн. удалений ресурсов) |
