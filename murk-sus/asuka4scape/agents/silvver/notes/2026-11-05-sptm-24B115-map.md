## 1. Что уже доказано по нашей сборке (не перепроверять)

- `FUN_fffffff0270adf30` = UAT MAP_BEGIN. Скип проверки прав для страницы,
  у которой `paddr == uat_instance[0x68]` (`gpu-region-base` / TTBAT), **остался**;
  для типов {2,3,5,6,7,9,10} на этом paddr — паника.
- `FUN_fffffff0270e1168` — проверка FTE-типа и max-permissions по текущему dispatch id
  (таблицы `0x27092228` bitset / `0x27092230` maxperm, stride 0x90).
- `FUN_fffffff0270abc74` — release/invalidate контекста: TTBAT-записи обязаны иметь
  valid-биты, иначе panic `TTBAT already contains invalid entries`.
- В сборке есть violation-имена `VIOLATION_UAT_ILLEGAL_TTBAT_MAPPING` / `_LOCK` (0x2700513f / 0x27005256).
- Device-тест (SPTM272Probe.ipa, 24B115): AGX/IOGPU user client открывается типом 1,
  но **все селекторы 0x00..0x37 → 0xe00002c2** без приватного энтайтлмента;
  `IOSurfaceAddress` трактуется как virtual64 (owningTask != 0); DART — not privileged.
  => firmware-путь к TTBAT из песочницы закрыт диспетчером, не только open().

## 3. Открытый вопрос №1 (ключ ко всему)

**Есть ли в нашем 24B115 фикс из b3?** Версия 820.40.24 > 820.40.23 косвенно говорит «да»,
но это не доказательство: нумерация может идти отдельно по SoC.

Проверка (одна команда, отправлена админу, msg 27):
```python
d=open('02_KERNEL/sptm/27.2/sptm.macho','rb').read()
for s in [b'uat_sync_outer_tlb_sapt_flush',b'uat_dekker',b'VIOLATION_T8110_DART_UNGANG_GAPF_RACE',
          b'verify-gmmu-tlbis-at-sync',b'gmmu-tlbi-verification-reg',b'Failed to verify TLBI']:
    print(s, d.find(s))
```
- Если `find == -1` для всех → гонка **жива** на 24B115, это лучший кандидат:
  окно PTE-write → TLBI, доступное из GPU/UAT-пути.
- Если строки есть → класс закрыт, TTBAT/TLBI официально снимаем с рассмотрения.

## 4. Если гонка жива — что смотреть

1. Найти в нашем бинаре аналоги `sapt_update_permissions_uat_unmap_sync` /
   `sptm_uat_remove_ctx_id` (по строкам внутри функций, не по адресам T8150).
2. Проверить порядок: запись PTE → `uat_sync_outer_tlb_sapt_flush`; отсутствие
   `dmb ish` между ними.
3. Достижимость: UAT-мутации инициирует XNU (pmap) по запросу GPU-драйвера.
   Device-тест показал, что AGX/IOGPU-селекторы из песочницы недоступны,
   значит нужен либо другой user client (Scaler открывается), либо kernel-путь.

## 7. IOUAT: firmware-объект, vtable и KASLR-формула (2026-11-05, вечер)

### 7.1 Что отдаёт IOGPU selector 1 (проверено по байтам 24B115)
`0xfffffff009947444` (IOGPU `__TEXT_EXEC` 0xfffffff0099407d0, off 0x2943000+0x444):
```
ldr x8,[x2,#0x58]     ; structureOutput
ldr x9,[x0,#0xf8]     ; provider
ldr x1,[x9,#0x1e8]    ; provider+0x1e8 = device+0x548
mov x0,x8
mov w2,#0x40
bl  0xfffffff009984e4c  ; memcpy
```
Размер вывода не проверяется: всегда 0x40.

### 7.2 Откуда берётся device+0x548
AGX `__TEXT_EXEC` = 0xfffffff008165300 (НЕ 0x8165000 — старый сдвиг −0x300):
```
0x81785e4 bl 0x8216350(dev, fn, 0)   ; объект
0x8178628 bl 0x8216730(2, dev, obj)
0x817862c str x0,[x19,#0x548]
```
`0x8216730` -> GOT `0xfffffff007ca5a68` (`0x80110000039ea074`) -> `0xfffffff00a9ee074`.
Это `IOUnifiedAddressTranslator::getFirmwareAddressSpaceHandle()`:
```
0xa9ee078 ldr w9,[0xadd7700] ; cmp #1 ; b.ne panic "IOUAT not enabled"
0xa9ee088 ldr x0,[0xadd7728] ; ret
```
То есть sel 1 копирует первые 0x40 байт firmware-объекта IOUAT из глобала `[0xadd7728]`.

### 7.3 Класс объекта и vtable (главное)
Инициализатор IOUAT 0xfffffff00a9ebf40; две ветки по `[0xadd7708]`:
```
state==0 (0xa9ec06c): x0=[0x7c68058]; bl 0xa9ec60c; str x0,[0xadd7728]
state==1 (0xa9ec0fc): new(0x570);   bl 0xa9ec758; str x0,[0xadd7728]
```
Оба конструктора ставят один и тот же vtable:
```
0xa9ec764 adrp x16,#0x7c67000
0xa9ec768 add  x16,#0xf08
0xa9ec76c add  x16,#0x10        -> 0xfffffff007c67f18
0xa9ec778 pacda x16,x17         ; x17 = x0 | 0xcda1<<48
0xa9ec77c str  x16,[x0]         ; q0
0xa9ec760 str  w8(1),[x0,#8]    ; q1 low32 = 1
```
vtable `0xfffffff007c67f18` (dataconst, chained fixups сходятся):
```
+0x90 -> 0xa9ecb48  getPageTablePhysicalBaseAddress (лог 0xa9ecb90, op 0xbee7)
+0x98 -> 0xa9ec9d0  getPageTableEntry               (лог 0xa9eca14, op 0xbee5)
+0xa0 -> 0xa9ec94c  mapToPhysicalAddress             (лог 0xa9ec984; = getPTE & ~0xfff)
+0xa8 -> 0xa9ebe30  init/attach (вызывается конструктором с 4 арг.)
```
AGX импортирует IOUAT напрямую через GOT 0x7ca5a60..0x7ca5a90:
0xa9ec60c (make), 0xa9ee074 (getFirmwareAddressSpaceHandle), 0xa9ee0d0, 0xa9ee210,
0xa9ee318, 0xa9ee854, 0xa9ee018, 0xa9ed1e4, 0xa9eec08.

### 7.4 KASLR-формула (закрывает статическую часть задачи #2)
PAC подписывает только старшие биты, low32 не меняются:
```
slide = ((q0 & 0xffffffff) - 0x07c67f18) & 0xffffffff
__TEXT      = 0xfffffff007004000 + slide
__TEXT_EXEC = 0xfffffff00814c000 + slide
```
Проверки на дампе: `q1 & 0xffffffff == 1`; биты 63:48 — PAC-подпись (не 0xffff),
биты 47:32 около 0xfff0 (+carry). Скрипт: `scripts/kaslr_from_q0.py`.

Ограничения: формула верна, если sel 1 действительно отдаёт объект из [0xadd7728]
(статически подтверждено) и если объект уже сконструирован (q0 != 0). Если q0 == 0 —
IOUAT не инициализирован/не включён, sel 1 даст NULL-deref в memcpy (паника).

### 7.5 mapToPhysicalAddress ≠ UAT MAP_BEGIN
`0xa9ec94c` только логирует VA и вызывает vtable+0x98 (getPTE), затем маскирует
результат до страницы. Реальные UAT-операции — через `[this+0x20]` и хелпер
`0xa3825a8(opcode, in, inSize, out, outSize)`:
```
op 0xbee5: in 8 байт (VA), out 8 байт (PTE)
op 0xbee7: in 4 байта (index 0/1), out 8 байт (PA корневой таблицы)
op 0xbee4: in 16 байт (addr,val), out 1 байт (bool)
```
Т.е. наружу торчат только read-only трансляции; MAP_BEGIN ищется отдельно
(кандидат — методы 0xa9ece5c / 0xa9ed01c / 0xa9ed644, +0x70..+0x88).

### 7.6 Открытые вопросы
1. Кто в ядре вызывает UAT MAP_BEGIN с paddr и может ли paddr прийти из IOGPU client.
2. Полный список вызывающих 0xa9ec94c / 0xa9ec9d0 (нужен полный kernelcache —
   локальная копия kc115.bin обрезана на 0x980000, дальше нули; качаю полный файл).
3. Устройство: sel 1, out 0x40, q0/q1 -> формула 7.4.

## 8. Кто импортирует IOUAT (24B115)

Скан полного `__DATA_CONST` кернелкеша (сегмент `0xfffffff007bb8000`, 0x548000 байт —
все kext-секции внутри): chained-fixup'ы на функции IOUAT есть **только у AGX**:
```
0xfffffff007ca5a40 -> 0xa9ed1e4  retain
0xfffffff007ca5a48 -> 0xa9eec08
0xfffffff007ca5a50 -> 0xa9ee0d0  setClientContextID
0xfffffff007ca5a58 -> 0xa9ee210  removeClientContextID
0xfffffff007ca5a60 -> 0xa9ec60c  make
0xfffffff007ca5a68 -> 0xa9ee074  getFirmwareAddressSpaceHandle
0xfffffff007ca5a70 -> 0xa9ee318  doMap
0xfffffff007ca5a78 -> 0xa9ee854  doUnmap
0xfffffff007ca5a80 -> 0xa9ee018  getMode
```
Плюс сама vtable IOUAT в `__DATA_CONST` (0x7c67f18). IOGPU — 0 ссылок.

### Вызывающие doMap в AGX
GOT-стаб `0xfffffff008216740` (adrp 0x7ca5000 + add #0xa70 + ldr + braa).
Call sites:
```
0xfffffff0081fcb78, 0x81fccb4, 0x81fcdb0, 0x81fce60  (функция 0x81fc968)
0xfffffff0081fde40                                    (функция 0x81fdc28)
```
`0x81fc968` = `AGXSecureGart::mapInThisGart(AGXSecureMemoryMap *, AGXPageTableEntryFlags)`
(строка 0x712260b в kernel `__PRELINK_TEXT`), `0x81fdc28` = unmap-аналог;
`0x81fdf54` содержит make + getFirmwareAddressSpaceHandle (init класса).
Стаб doUnmap `0x8216750`, call sites 0x81fc1f0/0x81fc2c4/0x81fc444/0x81fc4ec/0x81fda08.
Set/remove CTXID: 0x81fd620 / 0x81fd5b8.

### Смысл
- AGXSecureGart — secure MMU (secure/protected content), связан с AGXSecureMonitorG14.
- Аргумент paddr в doMap не передаётся: он берётся из физических сегментов
  IOMemoryDescriptor (см. отчёт id 16).
- Значит путь «userland -> произвольный paddr -> SPTM UAT MAP_BEGIN» через IOUAT
  не просматривается: единственный клиент — secure GART, дескрипторный.
- Осталось проверить kernel-internal вызовы doMap/mapToPhysicalAddress (нужен полный
  kernelcache; локальная копия обрезана, качаю целиком).

## 9. Полный скан kernel text: у IOUAT нет внешних kernel-вызовов (2026-11-05)

Покрытие: `__PRELINK_TEXT` 0xbac000, `__TEXT_EXEC` 0x2924000, `__TEXT_BOOT_EXEC` 0x8000
(файл качал целиком; не хватает только `__PRELINK_INFO`, он не нужен).

Все `bl` на entry points IOUAT:
```
0xa9ec078 -> 0xa9ec60c  make (init)
0xa9eca94 -> 0xa3825a8  PPL ioctl helper (getPageTableEntry)
0xa9ecc0c -> 0xa3825a8  PPL ioctl helper (isPageFaultExpected)
0xa9ecda4 -> 0xa3825a8  PPL ioctl helper (getPageTablePhysicalBaseAddress)
0xa9ee62c -> 0xa382400  PPL map wrapper (doMap)
0xa9eeb8c -> 0xa9ee854  doUnmap (rollback в doMap)
0xa9eece0 -> 0xa3825a8  PPL ioctl helper (setClientContextID)
```
Внешних вызовов doMap/mapToPhysicalAddress/getFirmwareAddressSpaceHandle нет.
Единственный внешний клиент — AGX через GOT 0x7ca5a40..0x7ca5a90 (раздел 8).

Поправка к отчёту 16: stride массива сегментов **0x28**, не 0x20:
`0xa9ee574 add x13,x28,x28,lsl#2; 0xa9ee578 add x11,x24,x13,lsl#3`;
обёртка `0xa382400` проверяет `umulh count*0x28`. Поля: +0 va, +8 pa,
+0x10 len, +0x18 flags(word), +0x20 резерв.

Инструмент: `/tmp/opencode/kc_scan_calls.py` (wait_full отключать — сервер отдаёт
`__PRELINK_INFO` как текст, полный размер не достигается; код весь в первых 0x3a74000).

### Итог по UAT
`userland -> произвольный paddr -> SPTM UAT MAP_BEGIN` через IOUAT закрыт:
1) paddr в doMap берётся из IOMemoryDescriptor;
2) doMap вызывает только AGXSecureGart (secure MMU);
3) IOUAT импортирует только AGX;
4) kernel-internal вызовов нет.
