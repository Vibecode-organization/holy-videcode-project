## Формат импортов (важно для всех kext'ов)

`__auth_stubs` — трамплины `adrp x17,#0x7ff2000; add x17,x17,#X; ldr x16,[x17]; braa x16,x17`.
Значение в `__auth_got` имеет вид `0x8011_0000_<u32>` где `<u32>` — **file offset
целевой функции в kernelcache**. Проверено на 9 трамплинах: все низкие 32 бита
попадают в `0x2c..0x3a` МБ и конвертируются в валидный пролог (`pacibsp`/`bti`).

Следствие: внешние вызовы IOGPU резолвятся без символов.

## Что это значит для #5

1. Очередь уведомлений **создаётся по запросу пользователя** (sel 14) с
   контролируемыми `count` и `size`; `size >= 0x2a`, `count >= 1`.
2. Её буфер отдаётся GPU отдельным маппингом (`+0x18`), а адрес маппинга
   возвращается в userland (`out[0]`). То есть это **штатная разделяемая
   память**, а не kernel-private структура.
3. Ядро не разбирает содержимое очереди: единственные обращения к `[+0x10]` —
   `vt+0xa0` (получить descriptor) и `vt+0x98` (port). Значит порча записей
   очереди сама по себе не даёт kernel R/W.
4. **Лид на GPU OOB:** `count` и `size` независимы, `size` — 32-битный.
   Если очередь считает `size + header` в 32 битах, `size` около `0xffffffff`
   даёт wrap → маленький буфер при большом заявленном объёме, и GPU пишет за
   границу. Это ровно тот класс бага, который описан как «GPU OOB».

## Догон: класс [+0x10] и проверка арифметики (отчёт 23)

`[+0x10]` в `IOGPUNotificationQueue` = **IODataQueue**.

- метакласс-глобал: `0xfffffff00ad97f50` (аксессор `0xfffffff00a9b32c8`)
- `MetaClass::alloc` `0xfffffff00a9b3348`: size `0x28`, vtable `0xfffffff007c38830`
- `withEntries(numEntries, entrySize)` `0xfffffff00a9b3b74`
- `initWithEntries` = vtable `+0x88` = `0xfffffff00a9b20e0`

Проверки (hard negative по переполнению):

```
cmn w1,#1 ; b.eq reject        ; numEntries == 0xffffffff
cmn w2,#5 ; b.hi reject        ; entrySize >= 0xfffffffb
add x8,x8,#4                   ; entrySize+4
add w9,w1,#1                   ; numEntries+1
udiv w10,w10,w9 → 0xffffffff/(numEntries+1)
cmp x8,x10 ; b.ls alloc        ; только потом умножение
```

Формула буфера: `round_page((numEntries+1)*(entrySize+4) + 12)`,
`cmn w1,#0xd` + `b.hi` и `cmp x21,x8` защищают и округление.
Буфер — `IOBufferMemoryDescriptor`, `[+0x18]`, `entrySize` в `[+0x20]`.

Значит `size ≈ 0xffffffff` не даёт wrap: undersized GPU-аллокации через
селектор 14 нет.

### update_pte — что удалось и что нет

`IOGPUMemoryMap::update_pte(uint32_t, IOMemoryDescriptor *, IOMemoryDescriptor *)`
локализован по строке-подписи `0xfffffff007830202`: она используется как *имя
функции* в failure-логе `IOLog`-вызова (`bl 0x9984c2c`, x3 = `0x783075e`
«file:line»). Единственная функция, которая её грузит, — **`0xfffffff00997f744`**.

Тело:

```
cbz x3 -> x20 = 0
[+0x20] vt+0xb0(x3)          ; получить байты/длину дескриптора
trace id 0x851801a5
vt+0xf8 (self) с (x1=idx, x2=desc1, x3=desc2)
если w0 == 0 -> лог с подписью update_pte
```

Проблема: для vtable `0x7fef940` слот `+0xf8 = 0xfffffff00a8edee0` =
`mov w0,#0xe0002c7; ret` (kIOReturnUnsupported, базовая заглушка). Ни один из
51 класса IOGPU не переопределяет `+0xf8`:

```
for each class vtable: vtable+0xf8 -> все либо -0x..., либо вне IOGPU
```

То есть либо реальный класс объекта — подкласс, которого нет в списке
`classes_iogpu.tsv`, либо vptr инстанса — `0x7fef828` (его ставит dtor
`0x9997eeb0`), а не `0x7fef940`, и тогда `+0xf8 = 0x9997f8b0` (`return 0`).

Следующий шаг: просканировать **все** qword-таблицы в
`__DATA_CONST,__const` (0x7fe8e10..0x7fefde8), а не только известные vtable, и
найти таблицу, у которой `+0xf8` указывает в код IOGPU; от неё получить
владельца и `init`. Полезные факты для этого: `update_pte` вызывает свою
подпись-лог только при ошибке, trace-id `0x851801a5`, тело `0x9997f744`.

Первый проход «все окна в `__const`, у которых `+0xf8` смотрит в код IOGPU»
дал ~500 кандидатов, почти все — сдвинутые копии одного и того же региона
(0xfec8c0..0xfefc80). Это шум: любое 8-байтное окно внутри таблицы даёт
попадание. Следующий проход надо фильтровать жёстче:

1. `V - 0x10` == 0 (offset-to-top) и `V - 0x08` — typeinfo (PAC-указатель);
2. `[V]` == delete-stub (`0x999841bc` / `b 0x99844ec`);
3. `[V+8]` — реальная функция (не `brk`);
4. только тогда смотреть `+0xf8`.

Полезные константы: delete-стаб `0xfffffff0099841bc`, `hint;brk #1` —
`0xfffffff009841c4`, «unsupported» `0xfffffff00a8edee0`
(`mov w0,#0xe0002c7; ret`).

## metaclass-vtable vs instance-vtable

### 1. Диспетчер-таблица IOGPUDeviceUserClient — точный формат

Таблица: `0xfffffff007fea200`, **56** записей, шаг **0x18**.
Формат записи (проверено на sel 14 = `{2,0,0,0x10}`, что совпадает с отчётом 22):

```
struct { uint64_t handler; uint32_t in_scalar; uint32_t in_struct;
                        uint32_t out_scalar; uint32_t out_struct; };
```

Полный дамп — `evidence/iogpu_dispatch_24B115.tsv` (sel / handler / 4 размера).
Ключевые: sel 14 → `0x99947c64` (2 скаляра, out 0x10); sel 25 → `0x99947de4`
(4 скаляра, in_struct `0xffffffff`, out_scalar 1); sel 26/27 — struct 12/4.

Осторожно: раньше в заметке фигурировало «sel — поле u32 в записи»; это неверно,

### 2. IOGPUDeviceShmem: реальный размер и init

- метакласс-хранилище `0xaf22420`; classSize из `OSMetaClass` ctor = **0x68**;
- `alloc` (метакласс-vtable +0x68) = `0x99951c38`: `kalloc(rec=0x7ff03e8, 0x68)`,
  база-init `0x9994d73c`, затем vptr = **0x7fec318** (instance vtable);
- фабрика `0x99951da0`: alloc 0x68 → init `0x99951e3c` → при ошибке release;
- init `0x99951e3c` пишет: `+0x20` (x1), `+0x28`, `+0x40`, `+0x48`, `+0x58`, `+0x60`,
  вызывает импорты `0x99848fc`, `0x998471c`, `0x998477c`, `0x998473c`, `0x998437c`
  (создание IOBufferMemoryDescriptor / map / wire-подобные шаги).

**Вывод:** записи за пределы 0x68 нет — максимум `+0x60`. Моё прежнее подозрение
про «+0x8c при size 0x68» было ошибкой: `0x9995245c` — это **метакласс-метод**
(`meta_vt 0x7fec3e0 + 0x118`), а не instance-init, и его x0 не обязан быть shmem.

### 3. IOGPUKernelMappedMemory

- classSize **0x40**, `alloc` `0x99951590` (`kalloc rec 0x7ff03a8`), instance vtable **0x7fec1c8**;
- `getKernelData()` = метакласс-метод `0x99951fe8`:
  `return *(void**)(self+0x50) + f(self)`, где `f = 0x999517f0`.
  `0x999517f0` читает `self+0x20`, `self+0x30`, `self+0x38`, `self+0x50` и сравнивает
  смещение с `[io+0x1b0]`/`[io+0x1b4]` (границы аллокации), логирует подпись
  `"getKernelData"` при ошибке.
- То есть это **kernel VA** (`base + offset`), не GPU VA.

Открытый вопрос: методы читают `+0x50`/`+0x60`, а classSize = 0x40. Либо объект
аллоцируется не через этот alloc (фабрикой большего размера), либо поле относится
к другому объекту. Не считать багом без проверки — надо найти фабрику kmm.

### 4. GPU-VA: где живут маппинги

`IOGPUMemory::createGPUMappingInTaskAtAddressLengthAlignment` = `0x99431c4`:

```
if (flags & 0x80) -> отказ
lock [self+0x48]
arr = ([self+0x50]==2) ? self+0x60 : *(self+0x58)
for i < [self+0x54]:                       // count
    m = arr[i]
    if (m->addr == want) { ... }           // [m+0x20] == адрес
unlock
... [self+0x10] vt+0x5a8(...) -> новый map-объект
... map vt+0xb8(x1,x2)  (или vt+0xb0)     // привязка/адрес
... при ошибке vt+0x28 (release)
```

`update_all_pte` = `0x9943ea0`: для того же массива вызывает
`0x9997f744(map, idx, descA, descB)` на каждый элемент; ошибка → откат уже
сделанных. `0x9997f744` — обёртка: `[+0x20] vt+0xb0(descB)` → длина, trace-id
`0x851801a5`, затем **`map vt+0xf8(idx, descA, descB)`**, при 0 — лог с подписью
`"update_pte"`.

### 5. ИСПРАВЛЕНИЕ (важно)

`classes2.json` (и все мои прошлые «vtable») — это **metaclass-vtable**, а не
instance-vtable. Доказательство: в них `+0x68` = `alloc` (`0x99951c38` для shmem,
`0x99951590` для kmm, `0x99946cd8` для user client), а сам `alloc` ставит объекту
**другую** таблицу:

| класс | metaclass vt | instance vt | size |
|---|---|---|---|
| IOGPUDevice | 0x7fed380 | 0x7fed280 | 0x120 |
| IOGPUDeviceUserClient | 0x7fea188 | 0x7fe9b88 | 0x130 |
| IOGPUDeviceShmem | 0x7fec3e0 | 0x7fec318 | 0x68 |
| IOGPUKernelMappedMemory | 0x7fec280 | 0x7fec1c8 | 0x40 |
| IOGPUVirtualMemory | 0x7fe8f78 | 0x7fe8e30 | 0xd8 |
| IOGPUNotificationQueue | 0x7fefd70 | 0x7fefcd0 | 0x30 |

Следствие: вывод из заметки «у IOGPUMemoryMap `+0xf8` = `0xa8edee0`
(kIOReturnUnsupported), значит PTE-путь мёртв» **недействителен** — я смотрел
metaclass-таблицу `0x7fef940`. Instance-таблица `IOGPUMemoryMap` этим путём не
получается: `MetaClass::alloc` у неё = `0x9997ef48` = `return 0`, то есть класс
абстрактный и создаётся не своим alloc'ом.

**Что это значит:** PTE-путь (`map vt+0xf8` → запись PTE) снова открыт, и искать
надо concrete-map-класс (тот, что возвращает `[io+0x10] vt+0x5a8`), а не
`IOGPUMemoryMap`.

### 6. Командные shmem (userland → kernel)

`0x99777d0` (обработчик `sIOGPUCommandQueueCommandBufferArgs`):

- по трём u32-ID из args ищет объекты в таблице очереди `[queue+0x488]`
  (lookup `0x9965b58`);
- у каждого берёт kernel VA (`vt+0x80` → `getKernelData`) и длину (`vt+0x98`);
- считает `base + len` с проверкой переполнения указателя
  (`eor; tst #-0x40000000000000`) — PAC-safe;
- дальше проверка `commands_start/end` против `cmdListShmemLength`
  (строки `"Invalid command list header..."`, `"invalid command list shmem ID"`).

Три типа shmem подтверждены строками: `kernelCommandBufferShmem`,
`segmentListShmem`, `sidebandBufferShmem` — все «map into kernel». То есть
пользовательские страницы живут в kernel VA, и парсер команд читает их напрямую.

### 7. PTE-путь: что ещё проверено после отчёта 24

- В **всём** `IOGPUFamily.__TEXT_EXEC` (0x99407d0..0x9984bec, 280 604 байт)
  нет ни одной инструкции `tlbi`, `dsb`, `dmb`, `isb` (capstone-скан).
  То есть кекст не делает собственного TLB/cache-обслуживания при «обновлении
  PTE». Если PTE и пишутся, то через импортированные IOMMU/`IOMemoryDescriptor`
  KPI, а не локальным кодом.
- Слот `+0xf8` у instance-таблиц IOGPU-классов почти везде указывает на
  заглушки `kIOReturnUnsupported` (`0xe0002c7`): `0xa9bf77c` (главное ядро)
  и `0xa8edee0`. Исключения — методы вида getter'ов (например, у
  `IOGPUVirtualMemory` `+0xf8 = 0x99413e4`: `if ([+0x90]==idx) { *out=[+0xa0];
  return [+0x98]; }`), а не writer PTE.
- Следствие: «writer PTE» надо искать не по слоту, а по вызовам IOMMU KPI.
  Кандидат — путь `createGPUMapping` → `[io+0x10] vt+0x5a8`, где `vt+0x5a8`
  у `IOGPUDevice` = thunk `0x9994d8e4` → `[vptr+0x70]`; реальный метод —
  в слоте +0x70 (там уже начинается код `IOGPUDevice`-уровня, а не общий
  OSObject-префикс).
- Полезные резолвы импортов (thunk в `__auth_got` → target, main kernel):
  `0x99843dc → 0xa8945f0`, `0x99844ec → 0xa895910`,
  `0x99848fc → 0xa9669d0`, `0x998471c → 0xa97bb2c`,
  `0x998477c → 0xa970b64`, `0x998473c → 0xa97bd8c`,
  `0x998437c → 0xa903134`, `0x9984adc → 0xa8962a0`,
  `0x99844dc → 0xa894d88` (OSMetaClass ctor), `0x998430c → 0xa902074`,
  `0x998427c → 0xa903020`, `0x998428c → 0xa2262a8`,
  `0x99842cc → 0xa226de0`.

### 7-испр. PTE-путь: поправка к разделу 7

Раздел 7 выше содержал ошибку измерения: обёртка `kc272.dis` по умолчанию
останавливается на первом `ret`, поэтому скан «всего сегмента» фактически
читал только начала функций. Корректные данные (`stopret=False`, 70 151
инструкция на 0x99407d0..0x9984bec):

- `tlbi` — **0**;
- `dmb ish` — **4**: `0x995cac8`, `0x995d0e4`, `0x9960df8`, `0x99829d4`;
- `dsb` / `isb` — 0.

То есть собственного TLB-обслуживания у кекста нет, но 4 `dmb ish` есть —
утверждение «барьеров нет вовсе» неверно и снимается. Остальные выводы
раздела 7 в силе: `+0xf8` у instance-таблиц — заглушка `kIOReturnUnsupported`
(кроме геттеров), writer PTE надо искать через IOMMU KPI, а `vt+0x5a8`
у `IOGPUDevice` — thunk на `[vptr+0x70]`.
